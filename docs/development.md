# Development

Use Node.js 24.13 or later. TypeScript runs directly in Node; `npm run check` checks types without emitting a build.

```sh
npm ci
npm run check
npm test
```

GitHub Actions runs type checks and the suite on Linux and macOS for every PR head; macOS also builds the menu app. CI uses fixture-owned temporary state and never deploys or reads production credentials.

Tests use fixtures and temporary state. They cover quota policy, provider routing, ownership, manual dispatch, monitoring, reopened tickets, merge approval, the journal, web authentication, and the web app's live stream. They do not require production credentials or prove compatibility with a live T3 build.

`package.json` keeps `private: true` to prevent accidental npm publication. This is a source-installed application.

For the native app, install Xcode Command Line Tools and run `npm run build:menu`. Building does not replace a running app. Use the [setup guide](setup.md#optional-interfaces) to install it after quitting the previous version. The app reads `status.json` and talks to the scheduler through the CLI; `T3Factory --render <dir>` draws the panel and every window page to PNG files from the current state and quits, which is how its views are checked without screen recording.

### Web interface

Ticket metadata uses the existing `Meta`, green `Tag` and `zap` icon for native `automationReady: true`. The compact symbol is named and titled "Automation ready". False or missing readiness shows no symbol; labels and queue eligibility do not imply readiness. Queue, session-ticket and dependency rows share this renderer. `test/run-filters.test.ts` covers queue/dependency projections; `queueTests.readiness()` and `sessionTests.readiness()` in the existing browser fixtures check live updates at desktop and mobile widths.

The browser app is plain ES modules served by `src/web.ts`; there is no bundler or build step. Preact, signals, and htm live in `web/vendor/` with their imports rewritten to relative paths, so the page needs no import map. The same script writes `web/vendor/icons.js` with the provider glyphs from `@lobehub/icons-static-svg` and the pull request and action glyphs from `@primer/octicons` as path data. Buttons are icon-only wherever the action is routine: `Button` takes an `icon` name and a `label` that becomes the accessible name and tooltip, and `More` is the arrow link from a section to its full page. Add a glyph to `scripts/vendor-web.ts` rather than inlining an SVG. After changing those versions in `package.json`, run `npm run vendor:web` and commit the result. The font is bundled in `web/fonts/` so the installed app works offline. Colours are CSS variables set by `web/lib/theme.js`; `web/lib/themes.js` is generated from a T3 Code checkout by `npm run vendor:themes -- <path>` and holds T3 Code's palettes, so the Theme picker offers the same themes as T3 Code in light and dark.

| Directory | Responsibility |
| --- | --- |
| `web/lib/` | Runtime re-exports (`h.js`), the fetch wrapper, the router, formatting helpers, and the store: signals plus every action that changes state |
| `web/ui/` | Component library: the `Page` frame and `Section` blocks every view is built from, `RowBody` and `Meta` for list rows, controls bound to config paths, the dropdown, segmented filters, the drag-to-reorder list, meters, tags, tables, timelines, dialog, toast |

Pages are real paths (`/runs`, `/runs/<id>`, `/models`, and so on) handled by `web/lib/router.js`; the server returns `index.html` for any extensionless path. Server state enters through `applyState` in `web/lib/store.js`. The page opens `/api/events`, a server-sent event stream that pushes the full state whenever the scheduler writes `status.json` or the config file changes. If the stream is unavailable, the existing top-bar indicator shows Retrying. The store recreates failed streams with exponential backoff capped at 30 seconds and uses one abortable background `/api/state` read at a time. Successful fallback reads run every 15 seconds; failed reads back off to 30 seconds. Background failures do not create persistent action notifications. Going offline immediately marks the connection Retrying and suspends network attempts. Coming online or returning to a visible tab prompts recovery, and a state event restores Live without discarding unsaved settings. A 401 still opens sign-in.

`test/web-reconnect.test.ts` exercises deployment outages, recovery, single-flight reads, teardown and expired sessions with a fake clock. A one-second clock signal keeps relative times and countdowns current between pushes. Inputs that take a `path` read and write the config signal directly, so adding a setting means adding one bound input. `test/web-ui.test.ts` imports the store and helpers in Node without a DOM; `test/web-live.test.ts` covers the stream and run endpoints.

`/start?ticket=APP-123` reuses the deck and Composer with a required named ticket; the bar is a project-key dropdown, a number field (empty means the next eligible ticket; a typed or pasted key such as `APP-12` keeps its own number and selects its project when that project is enabled, in the web and native bars alike), the model, a multi-pick of the limits to override (idle time, quota reserve, label limits; all picked by default, submitted as `overrideLimits: true`, otherwise as the list) and the start button. Routing and authentication never submit it. Pairing preserves the query; OIDC binds a validated local return path to its existing login transaction. The shared `startRun` boundary rejects duplicate named submissions while their request is queued, running or uncertain. Manual submissions in the browser and native app are accepted into ordered request rows, even while another ticket is being checked. Each row captures its ticket, model and override choices. One drain checks them in submission order through the existing endpoint or CLI; it advances when the dispatch check settles, without waiting for the implementation run. Refusals and errors retain their own row and do not stop later checks. Chain choices use the originating row's captured input and enqueue a new check. Confirmed run and chain starts leave the request queue immediately; answered prompts are replaced by their new check. Refusals, errors and unresolved choices remain until dismissed, or until the native app quits.

The browser persists pending and unsuccessful rows under `factoryOperations`, migrating the previous `factoryOperation` value and retiring previously saved successes and answered prompts. Reloading reconciles sent requests by ID before advancing the saved queue. Unsent rows retain their order and IDs. Uncertain outcomes are retained and never resent automatically; only a request confirmed absent from the server offers an explicit retry with the same ID. Retries join the end of the queue. The scheduler still owns serialization, fresh eligibility checks and duplicate protection.

After an operator renumbers tracker tickets, the SQLite metadata key `ticketKeyRevision` records the cutover identity. Status exposes that value, and newly queued named browser requests capture it. The dispatch endpoint records a terminal, not-launched refusal for requests from an older revision, including saved requests without a revision. Recovery never stamps old requests with the current revision. During this maintenance, stop the native app to discard its in-memory queue, drain server requests and plans, and migrate stored snapshots by ticket ID before restarting the service. Historical reports and idempotency receipts retain their original inputs.

### Scheduler service

`t3-factory run` starts one long-lived process (`src/service.ts`). It holds the store claim, a T3 client and a Kanvil HTTP client. Passes run in series from one queue. T3 thread events, Kanvil ticket events, configuration edits and control commands wake the queue. Configuration notifications compare normalized settings, so duplicate or delayed unchanged-file events do not add passes; invalid settings still report errors and a restored valid file wakes again. The `pollSeconds` timer covers maintenance and idle/quota transitions; it does not poll Kanvil inventories. Provider allowances retain their separate refresh timer.

Kanvil starts with `/api/v1/checkpoint`, refreshes project snapshots, and subscribes to `/api/v1/events` from that checkpoint. Snapshots carry the complete ticket labels, native difficulty, readiness fields, status category and version. The in-memory projection and processed cursor share one process lifetime: restart obtains fresh snapshots rather than resuming a cursor without its data. Inventory and dependency reads reuse the live projection until a change invalidates them. Ticket, claim and relation events fetch the changed ticket into the existing projection and invalidate dependency caches before advancing the cursor, then wake a pass. Deleted or moved-away tickets leave the projection. Project, workflow and other project metadata changes invalidate their project snapshot. Comment and evidence events advance the cursor without rescanning inventory. Duplicate events are ignored. An additional project-scoped stream revalidates access for each cached project, because the unscoped feed cannot deliver a membership revocation after access is removed. Scoped disconnects and revocations invalidate that project's caches; global disconnects discard all trusted inventory. Final launch also checks the selected project's connection and the event revision after its fresh reads. Inventory stays held until its stream reconnects; HTTP or in-stream `410 snapshot_required` resets the checkpoint and projection. Reconnect backoff only reconnects the feed, never scans tickets. The stream runs in its own read context so a manual deadline cannot cancel it. Candidates fetch native server readiness once per invalidation and retain it with their ticket version, so a missing description, duplicate, hold or claim cannot repeatedly enter the ready queue. Final dispatch, completion and cleanup checks use fresh authoritative ticket reads.

Kanvil labels arrive on tickets, with no workspace association scan. Parentage uses native `parentId`, children are fully paged including archived tickets, and `blocks` edges retain their canonical source/target direction. The existing dependency walker uses that shared projection for inherited blockers and umbrella handling. Workflow catalogs expose native categories to both interfaces, including custom states. `test/labels.test.ts` covers HTTP payload validation, ownership, safe errors, hierarchy pagination, SSE replay, duplicate events, snapshot recovery and cache reuse. Scheduler regression fixtures use `test/tracker-fixture.ts`; they do not stand in for HTTP/SSE contract checks. No production credential or live ticket mutation is used by these tests.

The service listens on `control.sock` in the state directory (`src/control.ts`). `t3-factory dispatch`, `once`, `doctor`, `job-stop`, and `plan-cancel`, and the web server's dispatch, stop, and cancel endpoints, send their command there: dispatches, checks, dry runs, and diagnostics run as a pass on the scheduler's queue and return its decision; stops and cancels return their result and wake a pass. Without a running service they do the work themselves, as before. Before a launch the scheduler re-reads the ticket's labels from the workspace and its blockers, so a label or relation that changed since the queue was read stops the start.

Explicit operator commands take priority over pending background passes, display quota refreshes, and cleanup, while retaining command arrival order. Active background work cooperates at phase and batch boundaries: a command cancels a disposable read batch, waits for every started sibling and teardown to settle, then runs before later batches. The suspended continuation rejoins the same queue with its completed batches intact. After three commands run while background work is pending, one background segment runs; cancelled batches finish uninterrupted retries, then hand off and refresh any snapshot changed by intervening commands before continuing. Ticket examination uses batches of six and cleanup projection yields every 64 items. Wake bursts share one pending pass; a change during an active pass can queue another. Dispatch and stop commands refresh their T3 client from current configuration when they execute. Dispatch also reads current ticket state and forces the selected provider's quota refresh before launch. Structured pass diagnostics keep `ms` for active execution and add numeric `queueWaitMs` for the preceding queue wait.

A resumed read batch refreshes its snapshot after any intervening command. Retained dependency caches share successful reads and evict rejected promises so cancellation cannot poison the next batch attempt. Final dispatch validation re-reads labels, dependencies, ownership, activity, quota and configuration; a foreground launch consumes its slot first, including project-wide discovery ownership across providers and the waiting cap. A partially invalidated ticket inventory keeps the previous Up next snapshot and requests a fresh pass after completing its remaining batches. Cleanup retains completed Git discovery for unchanged repositories; job and cleanup lifecycle notifications invalidate the affected repositories before its projection publishes current jobs, actions and threads. Session collection checkpoints retain their durable cursors. Durable launch ownership, Stop and workspace removal remain indivisible: their external outcomes settle under the existing bounded or uncertain-outcome contract. Shutdown cancels disposable reads, resumes suspended continuations to drain them, and retains accepted foreground commands.

Manual dispatch has one pre-launch deadline, `manualPrelaunchSeconds`, default 60. It starts at scheduler acceptance and includes queue wait, connection setup and read-only validation. CLI callers can supply `--request-id UUID`; web and native submissions always do. The existing operation record in `web-requests/` carries queued/checking/launching progress, the current read stages, acceptance/update/deadline timestamps and the eventual result. Health and `status.work` identify active work, its stage and age, and pending queue depth. `manual-phase` diagnostics use the same request ID and fixed stage names, with phase durations; tracker errors retain a category or HTTP status without logging server payloads.

An expired queued request receives a durable `manual-deadline-exceeded` result with `notLaunched: true` and is skipped when selected. During checking, cancellation reaches T3 and Kanvil HTTP reads and T3 RPC reads. The queue still drains started siblings and client teardown before selecting its next writer. No deadline races an abandoned dispatch continuation. Manual checks leave unrelated monitor interruption and workspace cleanup to ordinary service passes.

The final deadline check and durable job or chain ownership have no asynchronous gap. Ownership ends the deadline. A lost launch response remains uncertain with its existing job/thread or plan ID and is never automatically resent. Restarted pre-launch requests become not-launched outcomes; owned requests reconcile from saved job/thread or chain evidence, retaining uncertainty when acceptance cannot be confirmed. Web reloads and native request restoration reuse those same records. Successful launches leave the visible queue immediately. Older records without progress say that scheduler progress is unavailable rather than claiming a ticket check has started.

Shutdown refuses new commands, keeps health requests responsive, drains accepted commands, and skips pending background work. It stops event and maintenance scheduling and waits for active queue work and aborts/drains the Kanvil subscription before closing the shared clients and store. A rejected command or background pass does not stop the queue.

### Session ticket collection

Creation reports may announce a completed ticket batch, then list its tickets under Markdown section headings or in a Markdown table. The parser carries that affirmative context through the associated lists and tables, resets at ordinary prose or existing/related/next sections, and treats each list item independently so explanatory sentences do not suppress later entries. A table needs a Ticket, Issue or Key column and a header separator; only that column supplies references, so descriptive cells can mention existing tickets without collecting them. Explicit ranges and line-ending same-project numeric shorthand expand to at most 200 keys per expression. Future intent, negations, quoted/code content, illustrative tables without a creation introduction and unrelated mentions remain excluded; tracker workspace and creation-time checks still confirm every candidate.

`SessionThread.reportVersion` versions durable parser progress. A legacy eligible thread is walked again through the existing bounded cursor/backfill pipeline even when its timestamp is unchanged. The version and partial cursor survive failures and restarts; pending lookup retries, stored provenance, dismissal and consumption markers remain intact. No live database edits or dispatch replay are needed. `test/session-tickets.test.ts` covers sectioned/ranged reports, negative grammar, legacy recovery, failed pages, restart, idempotence and recovery into `status.json` while automation is paused.

Markdown headings form their own parser blocks even when their list immediately follows without a blank line. An affirmative batch introduction therefore carries through a foundation list and subsequent creation tables. Existing, related, example and not-filed sections still terminate that context.

Historical tracker task links keep their legacy ID as a separate reference kind. Confirmation uses the same explicit import provenance parser as state migration, matching source IDs or unambiguous source keys from workspace-scoped project snapshots and checking the original creation timestamp against the session/report lifetime. Native import timestamps and reused current numbers are not creation evidence. Snapshot reads are shared within the batch, invalidated by tracker revision changes, and yield through the existing background read boundary; malformed, ambiguous or unavailable provenance stays pending with backoff. Recovered rows keep native identity/status and original creation time, so completed tickets remain hidden. Migration preserves the parser version actually used rather than certifying old history as newly parsed.

Tracker key confirmation reads Kanvil's native project ticket endpoint; unscoped references resolve through `/api/v1/tickets/resolve`. Only HTTP 404 with the stable `not_found` code retires a missing creation reference. Other failures retain the reference for retry. Session-ticket metadata is invalidated immediately by Kanvil events, while conversation collection retains its bounded batches and durable provenance. Initial confirmation and ordinary refresh share revision-guarded publication so a concurrent event cannot be overwritten. Refresh resolves stable ticket IDs and updates current project, key and number together after a move, checking the workspace-scoped catalog before publication.

The shared tracker client distinguishes explicit server `NOT_FOUND` codes on task reads from other failures. Candidate confirmation discards those missing references for keys and task links; it never adds them or retries them as authentication failures. Plain not-found text, malformed errors, authentication failures and outages remain retryable. A failed refresh of an already listed ticket keeps its last reading and reports the failure, including explicit absence.

After every ordinary pass the service queues one background batch of `collectSessionTickets` (`src/session-tickets.ts`) behind any pending command, and queues another while the batch reports more work. A batch lists every top-level session T3 exposes (`T3.sessions`: settled and archived included, subagent and deleted threads excluded), reads changed sessions with `T3.conversation` (the bounded window, then older history pages by cursor, with items inherited from a forked thread dropped), confirms pending references with the tracker, refreshes listed tickets and marks consumed ones. Changed sessions and pending confirmations are processed newest-update first so recent reports precede historical replay. Both queues share the same comparator, including the timestamp of unfinished backfill. Each step is bounded (eight page reads, ten lookups, ten refreshes) so foreground commands never wait long.

Origin classification is stored as `upstreamReview` in the existing session scan record. Old records without a classification revisit their history through the same bounded backfill, even when the last-seen ordinal is already known. New candidate confirmation waits until the source is classified as ordinary. Existing rows and provenance survive unknown or failed reads; a confirmed review source is excluded by the shared projection rule. A missing continuation cursor is a retryable read failure, not proof of an ordinary origin.

Progress lives in the `session_threads` table: a session's `lastOrdinal` is the newest turn item processed, and an unfinished `backfill` holds the cursor of the next older page. A page's references are saved together with the cursor that follows it, so an interrupted read repeats the same page and never skips one; a failed read leaves the session's progress untouched and sets a five-minute retry deadline, so an outage neither loops on the same sessions nor starves the ones behind them. The first scan of a session walks history to its beginning; a later scan reads the window and, when the window no longer reaches `lastOrdinal`, walks back until it does. Unchanged sessions are not read.

A reference becomes a row in `session_tickets` only when the tracker returns the task in the configured workspace and the task's `createdAt` falls between the session's start and the report, so a ticket that is merely mentioned, or that predates the session, is not listed. A reference whose project the cached catalog does not know triggers one fresh catalog read per batch before it is dropped. A native `404 not_found` retires an unconfirmed reference. Other failed lookups stay pending with a growing retry delay, at most hourly. One task is one row whatever the number of reports; each report adds a source. Rows are refreshed from the tracker at most every five minutes. A native `404 not_found` on a saved ticket marks it missing and hides it from the actionable list without deleting its metadata or provenance. Missing rows are checked again after five minutes, including in realtime mode and after restart; a successful read restores the row with its current identity and status. Missing tickets do not fail collection. Other failed refreshes keep the old values, record the error and set the row's next read five minutes out, so an outage never loops on the same rows or starves the ones behind them. Failures, including a batch that cannot start because the configuration or the tracker client fails, are recorded as `sessionTickets.error` in status and never remove rows; the notice stays throughout retry backoff while any retained ticket row, reference, or still-listed session carries an unresolved failure, and clears once a batch finds none.

Dismissal (`t3-factory session-dismiss TASK_ID`, or the web page) sets `dismissedAt` on the row; the row remains so rescans, other sessions, refreshes and restarts cannot bring it back. A row is consumed when a Factory job for the task exists in any state other than a merely prepared or unknown dispatch, including runs started from the deck, the CLI, a chain or automation; the collector persists that as `consumed`. `writeStatus` publishes the remaining rows that are in their project's ready column (configured `readyStatuses`, else the first non-final column from the tracker), ordered by priority, project key and number, as `status.sessionTickets`. `test/session-tickets.test.ts` covers the service path, extraction, backfill and catch-up, interrupted reads, failed lookups, dismissal, consumption and membership with synthetic sessions and tracker answers.

Service passes reconcile reports, execution, ownership, and capacity before dispatch, then schedule completed-workspace cleanup as coalesced maintenance on that same queue. Each maintenance item performs one eligible job's existing cleanup step, then yields before queuing the next job at the tail. Each job is visited once per sweep; intermediate steps resume on the next ordinary pass. Startup and fallback passes schedule maintenance even with automation paused, and a failed dispatch still schedules it. Pending cleanup snapshots and blocked-retry timestamps remain in the job record across restarts. Cleanup failures retain their existing error and backoff without changing the dispatch result.

Standalone manual dispatch also defers cleanup, leaving the durable job state for the next service pass or ordinary `once`. Standalone ordinary `once` and direct `reconcile` callers keep inline cleanup. Dry runs and `doctor` neither perform cleanup nor schedule a maintenance sweep. Deferred maintenance uses the same fresh-read checks, terminal and subagent handling, process checks, and guarded removal as inline cleanup.

Initial shell and provider reads overlap. The final validation phase independently re-reads the shell, forced selected-provider quota, native ticket with its full labels and server readiness, dependencies, and open pull requests. Ticket and relation promises are shared only within that phase. Dependency reads fan out with a limit of six, while cycle detection follows each ancestry path. A failed phase waits for all reads it started to settle before returning; artifact cache updates, policy decisions, durable ownership, and launch remain sequential. Inventory snapshots never substitute for these final checks.

A named-ticket dispatch lists only that ticket's enabled project, across all columns and pages so its actual status can be reported. Dependencies outside that list reuse the live Kanvil snapshot or are resolved by ID with their complete native ticket metadata. Cross-project blockers, parent and child rules, final statuses, and inherited priority still apply. Dispatches without a ticket and the live queue continue to inventory every enabled project's ready columns; final pre-launch checks remain fresh.

### Chains

A manual dispatch of a ticket that waits on other tickets is not refused. The scheduler walks `blocks` relations, native parentId ancestry, and umbrella children through Kanvil (`blockerTree`) and answers `blocked-ticket-plan-required` with the whole tree. The caller then dispatches again with `--chain first`, which starts the highest-priority ticket in the tree that can start now, or `--chain all`, which stores a plan (`plans` table) and starts every runnable ticket within the run limits. Every pass advances active plans (`runPlans`), whether or not ticket automation is on: tickets start in priority order as the ones ahead of them finish in Kanvil, every launch still requires native automation readiness, and the target runs last. Only the launches made while the user chooses the chain carry manual policy; later continuations keep the automatic quota and idle policy, apply only the chain's recorded override, and use automatic models only when the chain was started with the automatic model. `t3-factory plan-cancel <id>` and `/api/plans/<id>/cancel` stop a plan; running tickets finish on their own. Active plans reach the page as `status.plans`.

### Journal

`Store.save` is the only job write path, so it records an event whenever a job is created, changes state, or gains a pull request. `Store.decide` records a check only when its outcome differs from the previous one or when it failed; a dispatch is journaled by the job it creates. Routine disabled checks update the latest decision without adding "Automation paused" events. Existing journal history is retained. Events live in the `events` table of `state.sqlite` (capped at 5000) and reach the page as `status.journal`; `/api/jobs/<id>/report` returns one run with its events and completion report. `t3-factory sources` (served as `/api/sources`) lists T3 projects, Kanvil projects with their native status categories, and project label catalogs so the projects page can pick instead of typing identifiers. `t3-factory job-stop <jobId>` asks T3 to stop a run's thread and the service reconciles at once; the web app's Stop button calls it through `/api/jobs/<id>/stop`.

## T3 compatibility

The integration uses application APIs that can change between T3 builds. Matching the T3 product name or having a provider signed in is not enough. The current client speaks T3 orchestration protocol v2 and requires:

- The `x-t3-orchestration-protocol: 2` header on every HTTP request, and `orchestrationProtocol=2` on the WebSocket URL.
- Authenticated HTTP snapshots from `/api/orchestration/shell` and `/api/orchestration/threads/<id>/bounded`.
- WebSocket tickets from `/api/auth/websocket-ticket` and the `/ws` endpoint.
- Effect RPC methods `server.getConfig`, `server.refreshProviders`, `orchestration.launchThread`, `orchestration.dispatchCommand`, `vcs.removeWorktree`, `subscribeTerminalMetadata` (stream; the first event is a terminal snapshot), and `terminal.close`.
- The `terminal:read` scope on the scheduler credential for `subscribeTerminalMetadata`, and `terminal:operate` for `terminal.close`. Without `terminal:read`, workspace cleanup stops with `EnvironmentAuthorizationError`.
- Provider model metadata and usage windows with timestamps, remaining-window information, and reset times.
- Thread launch input and the public `run.interrupt` and `thread.pull-request.watch` commands compatible with the payloads in `src/clients.ts`.

T3 hosts that predate protocol negotiation (v1) are not supported. When T3 rejects the protocol header, the client reads `/.well-known/t3/environment` and reports `T3 orchestration protocol mismatch` with the version the server requires.

Stop is shared by operator requests, stalled-monitor recovery, and verified-completion monitor cleanup through `T3.stop`. It reads fresh bounded control state, interrupts the newest preparing, starting, running, or waiting run with `holdQueue: true`, or the latest settled run when provider background tasks or active background turn items remain. Queued runs, persistent dynamic tools, rolled-back items, and inactive provider rosters do not supply work to interrupt. With no owning run it disables visible linked PR watches; no work is a successful no-op. It uses the public RPC commands, never internal `thread.stop`, provider-session detachment, or queue resumption. Mutation failures propagate without retry; callers retain ownership until T3 confirms the outcome. Protocol fixtures validate emitted commands at the fake public RPC boundary.

Liveness comes from each v2 thread's `status` (its latest run), `activeRunId`, `pendingRuntimeRequest`, and `pendingBackgroundTasks`. Only a pending human-facing request, such as an approval or question, means the thread is waiting for a person. `dynamic_tool_call` and `auth_refresh` requests are internal work and retain execution capacity. A `waiting` status without a human-facing request also retains capacity until T3 settles the handoff, without adding a "needs you" event. Unknown request kinds remain human-facing. Background tasks of kind `monitor`, including pull request watches, are passive monitoring, and kind `command` is a local process; any other kind, including unknown kinds, is active worker execution. An active run whose provider sessions are all `stopped` or `error`, on a thread unchanged for 30 minutes, is orphaned and does not count as executing. Human-facing requests and fresh runs are excluded from the probe; old internal requests and requestless waiting runs remain eligible. Detection reads `runs` and `providerSessions` from `/api/orchestration/threads/<id>/bounded`; a failed or ambiguous read keeps the run executing.

Dispatch launches a thread over RPC with a `worktree` workspace strategy. T3 creates the worktree from the project's workspace root, which must match the configured `repoPath`, and runs the project's setup script. The plain HTTP dispatcher does not prepare worktrees. The scheduler validates the fields it consumes and stops affected dispatches when the contract is incompatible. It does not edit T3's database or fall back to driving its UI.

Quota refreshes target the selected provider with `server.refreshProviders({ instanceId, refreshModels: true })`. Despite its name, `refreshModels` also invalidates T3's cached capability and usage probe. A refresh without that flag can return the old quota snapshot. Factory refreshes stale reads with cache invalidation and retries once if the probe still returns stale or unavailable quota. Two failed probes block the run and report that automatic refresh failed.

Run `doctor` against your actual T3 build before enabling automatic work. Live verification requires your own credentials and configured projects; keep those outside tracked files.

Command tasks do not count as provider execution or extend personal activity. Their unfinished running jobs still retain automatic-run reservations in `busyProviders`, because command notifications can resume them without another admission check. Verified completion and human-input waits release those reservations. A settled turn that yields to pending commands without a report is an unfinished background wait (`commandWait` in `src/policy.ts`): the commands' completion notification resumes the same job, so reconciliation keeps it `running` with reason `Waiting for background commands`, journals no "needs you", and retains its claim and workspace. A missing report authorizes no Stop, cleanup or redispatch. An awaiting-human report written before the job resumed from waiting, or before the latest user message, has been answered and does not describe the wait; the job records `resumedAt` when it sees that resume. Any other report goes through the usual verifier: valid complete or no-work reports finish the job despite leftover commands, explicit awaiting-human reports wait for a person, and invalid, mismatched or unverifiable reports keep their diagnostic. Stopped and orphaned runs, and a turn whose command roster has emptied without a report, still surface the missing-report diagnostic. Human requests, runtime handoffs and non-command workers retain their existing protection. Passive monitors still use the monitoring timeout; a mixed monitor/command roster never authorizes timeout cancellation.

Command cleanup extends the existing workspace-maintenance step and T3 stop helper. It validates the job report through the same completion verifier as reconciliation, including Done and merged delivery evidence even when a dismissed job's commands have already exited, then checks a fresh bounded projection and shell before interruption. Queued runs, pending requests, new user messages, non-command turn items or provider tasks, active subagents, changed ownership, shared bindings, and changed Git/report evidence hold cleanup. Persisted todo-list items are passive plan display, so their item status alone does not block verified cleanup. User messages after the report was written hold cleanup even when a dismissed job is only now being verified. The job's durable `commandStop` distinguishes requested, uncertain and confirmed outcomes. A request is saved before dispatch and is not resent while commands remain, including after restart. Confirmation requires a later empty roster; terminal and process-CWD guards still apply before removal. Tests in `policy`, `monitor`, `workspace-cleanup`, and `service` use isolated fixtures, including deferred Stop and injected races.

Completed-workspace cleanup closes the completed thread's idle T3 terminals with `terminal.close`, always passing `terminalId` and `deleteHistory: false`. It never closes a terminal that is starting or running a command, or one owned by another thread. It also requires `lsof` to verify process working directories. If the terminal snapshot or that check is unavailable or fails, the workspace is preserved. Removal uses `force: false`; workspace metadata updates use the expected worktree path to prevent changing a different binding.

## Changes and review

Keep runtime behavior documented in the relevant guide and examples aligned with the configuration schema. Use generic fixture names, domains, and paths. Review changes before committing, run type checks and relevant tests for code changes, and build the menu app when changing Swift code.

Documentation changes need link and example validation, not live ticket dispatches. Keep installation separate from development: the installers restart services and copy the runtime, so they are deployment commands rather than build checks.

`LOCAL.md` may contain private deployment instructions for a particular checkout. It is ignored by Git and is not distributed to contributors.

### Cleanup management

`src/workspace.ts` is the shared filesystem inspection and removal boundary for automatic cleanup and operator actions. It validates canonical registered Git identity, protects primary checkouts and tracked/untracked work, and confirms both directory and registration absence after T3 removal. `src/cleanup.ts` resolves each input path once per inventory and indexes bindings, jobs and actions by canonical path. Its indexing and projection loops yield after bounded batches so deadline and cancellation events can run. Review and removal always read fresh identity. It adds cross-job inventory, read-only evidence, expiring force reviews and durable operator action records. Normal cleanup may discard all ignored files after verified completion, merged HEAD and fresh idle/activity checks. The shared removal boundary rechecks identity and tracked/untracked contents after its final activity callback, then uses the T3 force flag only when ignored files require it. Explicit deletion review can override completion/content holds, but not live safety checks. Git status summarizes matching ignored directories instead of expanding dependency files. Review fingerprints skip disposable ignored contents; their total size stays unknown when that traversal is skipped.

Cleanup commands use the existing serialized service queue and offline claim. Inspection cancellation is a separate control command so it can cancel a read queued behind a pass. The browser reuses saved operations, `RunFilters`, `Segmented`, `RowBody`, `Meta`, `Tag`, `Facts`, `Section` and `Timeline`. The page lists every present worktree except primary checkouts, named by folder with its branch beside it, under one `Segmented` view (All, Unused, Blocked, In use) whose counts come from the inventory's group totals. Inventory projects each row's group, plain reason and next action together; `cleanupOutcomePresentation` in `web/lib/format.js` is the one place a recorded refusal becomes a group and an action, for the backend catalog and the browser alike: local changes, unmerged work and a thread resumed after its run finished become Blocked rows whose action is Delete anyway (`Resumed after completion` is its own overridable check in `inspectCleanup`), an open terminal or process makes the row In use, and refusals under rules that no longer apply (ignored files, the old Factory-only ownership rule, the old scan limit) return to Unused. Transient failures recorded by automatic maintenance (connection errors, a missing report) also leave the row Unused, because manual deletion verifies Git and live state itself. The force request still carries the reviewed folder name as its confirmation. A completed request reports the durable per-target outcome rather than treating exit code zero as removal. Saved outcomes overlay older inventory until its result snapshot catches up; `/cleanup` needs its own view because its inventory includes worktrees without any Factory run.

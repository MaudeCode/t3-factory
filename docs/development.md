# Development

Use Node.js 24.13 or later. TypeScript runs directly in Node; `npm run check` checks types without emitting a build.

```sh
npm ci
npm run check
npm test
```

GitHub Actions runs type checks and the suite on Linux and macOS for every PR head; macOS also builds the menu app. CI uses fixture-owned temporary state and never deploys or reads production credentials.

Tests use fixtures and temporary state. They cover quota policy, provider routing, ownership, manual dispatch, monitoring, reopened tickets, merge approval, the journal, web authentication, the web app's live stream, and the Inbox triage sandbox. Triage tests use two inboxes feeding two projects with different scope allowlists, a fake `claude` executable that records its argv, environment, working directory, and snapshot, a fake git remote, and a fake Kanvil client with seeded projections; they never run a live model. They do not require production credentials or prove compatibility with a live T3 build.

Integration failures use the shared `readPhase` boundary to retain the original failing phase and elapsed milliseconds, even when parallel reads drain later. `safeError` includes bounded error types, transport codes and nested causes in the existing logs and saved manual-request outcomes. For example, a truncated T3 response can report `t3.shell failed after 12ms: TypeError: terminated; caused by SocketError: [UND_ERR_SOCKET]: other side closed`. Four cause levels and 800 output characters cap diagnostics; URLs and credential patterns are redacted, and headers, bodies, stacks and socket objects are excluded. Cancellation keeps its original thrown value and deadline semantics; diagnostic formatting never retries a request or changes launch ownership. The T3 HTTP client separately permits one retry of an idempotent GET cut off with UND_ERR_SOCKET, sharing the original timeout/cancellation budget; POSTs are never replayed. `test/read-context.test.ts` covers a real truncated HTTP response, a later-draining sibling, persisted failure output, cancellation and redaction. The historical cause of an already-saved bare `terminated` message cannot be recovered by this change.

`package.json` keeps `private: true` to prevent accidental npm publication. This is a source-installed application.

For the native app, install Xcode Command Line Tools and run `npm run build:menu`. Building does not replace a running app. Use the [setup guide](setup.md#optional-interfaces) to install it after quitting the previous version. The app reads `status.json` and talks to the scheduler through the CLI; `T3Factory --render <dir>` draws the panel and every window page to PNG files from the current state and quits, which is how its views are checked without screen recording.

### Web interface

Ticket metadata uses the existing `Meta`, green `Tag` and `zap` icon for native `automationReady: true`. The compact symbol is named and titled "Automation ready". False or missing readiness shows no symbol; labels and queue eligibility do not imply readiness. Queue, session-ticket and dependency rows share this renderer. `test/run-filters.test.ts` covers queue/dependency projections; `queueTests.readiness()` and `sessionTests.readiness()` in the existing browser fixtures check live updates at desktop and mobile widths.

The browser app is plain ES modules served by `src/web.ts`; there is no bundler or build step. Preact, signals, and htm live in `web/vendor/` with their imports rewritten to relative paths, so the page needs no import map. The same script writes `web/vendor/icons.js` with the provider glyphs from `@lobehub/icons-static-svg` and the pull request and action glyphs from `@primer/octicons` as path data. Buttons are icon-only wherever the action is routine: `Button` takes an `icon` name and a `label` that becomes the accessible name and tooltip, and `More` is the arrow link from a section to its full page. Add a glyph to `scripts/vendor-web.ts` rather than inlining an SVG. After changing those versions in `package.json`, run `npm run vendor:web` and commit the result. The font is bundled in `web/fonts/` so the installed app works offline. Colours are CSS variables set by `web/lib/theme.js`; `web/lib/themes.js` is generated from a T3 Code checkout by `npm run vendor:themes -- <path>` and holds T3 Code's palettes, so the Theme picker offers the same themes as T3 Code in light and dark.

| Directory | Responsibility |
| --- | --- |
| `web/lib/` | Runtime re-exports (`h.js`), the fetch wrapper, the router, formatting helpers, and the store: signals plus every action that changes state |
| `web/ui/` | Component library: the `Page` frame and `Section` blocks every view is built from, `RowBody` and `Meta` for list rows, controls bound to config paths, the dropdown, segmented filters, the drag-to-reorder list, meters, tags, tables, timelines, dialog, toast |
| `web/views/` | Pages: login, deck, runs and run detail, session tickets, activity, models, capacity, projects, upstream, and the app root |

Pages are real paths (`/runs`, `/runs/<id>`, `/models`, and so on) handled by `web/lib/router.js`; the server returns `index.html` for any extensionless path. Server state enters through `applyState` in `web/lib/store.js`. The page opens `/api/events`, a server-sent event stream that pushes the full state whenever the scheduler writes `status.json` or the config file changes. If the stream is unavailable, the existing top-bar indicator shows Retrying. The same indicator is the notification area for background problems: `issues` in the store lists each source's error with the page it affects (session-ticket collection, and Session tickets starts that ended without starting), the indicator becomes a button with the problem count, and its popover shows each problem's plain title and cause with affected IDs and raw tracker wording behind Details. Problems never open the list on their own, so a reconnecting stream cannot flicker a notification; the list closes when the last problem clears. The store recreates failed streams with exponential backoff capped at 30 seconds and uses one abortable background `/api/state` read at a time. Successful fallback reads run every 15 seconds; failed reads back off to 30 seconds. Background failures do not create persistent action notifications. Going offline immediately marks the connection Retrying and suspends network attempts. Coming online or returning to a visible tab prompts recovery, and a state event restores Live without discarding unsaved settings. A 401 still opens sign-in.

`test/web-reconnect.test.ts` exercises deployment outages, recovery, single-flight reads, teardown and expired sessions with a fake clock. A one-second clock signal keeps relative times and countdowns current between pushes. Inputs that take a `path` read and write the config signal directly, so adding a setting means adding one bound input. `test/web-ui.test.ts` imports the store and helpers in Node without a DOM; `test/web-live.test.ts` covers the stream and run endpoints.

Manual submissions in the browser and native app are accepted into ordered request rows, even while another ticket is being checked. Each row captures its ticket, model and override choices. One drain checks them in submission order through the existing endpoint or CLI; it advances when the dispatch check settles, without waiting for the implementation run. Refusals and errors retain their own row and do not stop later checks. Chain choices use the originating row's captured input and enqueue a new check. Confirmed run and chain starts leave the request queue immediately; answered prompts are replaced by their new check. Refusals, errors and unresolved choices remain until dismissed, or until the native app quits.

The browser persists pending and unsuccessful rows under `factoryOperations`, migrating the previous `factoryOperation` value and retiring previously saved successes and answered prompts. Reloading reconciles sent requests by ID before advancing the saved queue. Unsent rows retain their order and IDs. Uncertain outcomes are retained and never resent automatically; only a request confirmed absent from the server offers an explicit retry with the same ID. Retries join the end of the queue. The scheduler owns independent admission, fresh eligibility checks and duplicate protection.

After an operator renumbers tracker tickets, the SQLite metadata key `ticketKeyRevision` records the cutover identity. Status exposes that value, and newly queued named browser requests capture it. The dispatch endpoint records a terminal, not-launched refusal for requests from an older revision, including saved requests without a revision. Recovery never stamps old requests with the current revision. During this maintenance, stop the native app to discard its in-memory queue, drain server requests and plans, and migrate stored snapshots by ticket ID before restarting the service. Historical reports and idempotency receipts retain their original inputs.

### Scheduler service

`t3-factory run` owns one SQLite ledger and runs independent asynchronous operations. Manual requests start immediately. Reconciliation, Up next inventory, cleanup, cleanup-catalog discovery, session collection, upstream release discovery and provider quota refresh have separate lifecycles. Automatic ticket, chain and upstream admission run independently for each provider. Automatic lanes require capacity and an automatic model before doing provider or inventory reads. Explicit chains remain independent of automatic model selection; one lane still checks their completion when both capacities are zero. Each assignment owns its own cancellation and mutation boundary, and runnable chain leaves prepare concurrently within capacity. A wake burst coalesces only another run of the same domain; it never queues a foreground request behind unrelated work. T3 lifecycle events wake work after a short leading-edge debounce; streaming text, item counts and visit-only updates invalidate shell reads without restarting every domain, Kanvil events invalidate immediately, and the fallback `pollSeconds` timer covers maintenance and idle/quota transitions without polling ticket inventories. The service arms that fallback independently of admission, so manual-only configurations retain maintenance and continuous events cannot postpone it. Normalized configuration comparisons ignore unchanged filesystem notifications.

Automatic selection plans a bounded batch and prepares its assignments concurrently. In-memory ticket preparation keys keep independent provider workers from selecting the same ticket while it is being checked. `Store.exclusive` orders conflicting job and worktree mutations by stable resource key; unrelated resources run independently. Capacity, label limits, waiting caps, active plans, discovery/upstream ownership, current configuration and duplicate protection are checked again immediately before a synchronous durable reservation. `jobs.task_id UNIQUE` is the final ticket fence. No external I/O is inside that commit. A launch reserved while another final quota read was in flight invalidates that read's reservation generation and causes fresh validation before the next commit. Execution heartbeats alone do not invalidate quota.

Manual named-ticket admission resolves that identity directly and does not reconcile unrelated jobs or list every ticket in a project. Automatic model choice uses configured model order and difficulty within available provider workers; the timing of independently ready providers can affect which provider reserves work first. Manual starts respect provider capacity unless the request includes the `providers` override, or `overrideLimits: true`. The shared `busyProviders` evaluator applies this policy at selection, preflight and final reservation for Auto and explicit models. Automatic starts and chain continuations still honor configured provider limits, including zero. Reconciliation runs separately and safely retains uncertain or unreconciled ownership.

The service's T3 client holds one multiplexed RPC connection. HTTP socket tickets and a read-only connection handshake are needed only when connecting or reconnecting. Caller cancellation interrupts its own request without closing a sibling's transport. A launch prepares and checks its connection before acquiring durable ownership, then uses that exact prepared connection instead of opening another socket after reservation. Failed prerequisites are definitive not-launched outcomes. Once submission may have happened, an error retains the same job/thread identity and is never automatically resent. Shell/provider snapshots and complete Git/PR reads share in-flight work with explicit freshness and independent consumer cancellation. Final checks still require fresh shell, selected-provider quota, ticket/dependency and PR evidence. Complete PR mention checks remain mandatory; search-index absence is not duplicate protection.

Kanvil begins with `/api/v1/checkpoint` and permission-filtered durable SSE. Ready inventory uses paginated `/api/v1/projects/{projectId}/eligibility`, obtaining native ticket metadata and server readiness together. Workspace ownership and each scoped project stream are checked before trusting those rows. Named references and final validation use authoritative ticket reads. ### Session ticket collection

Session tickets come first from the session's own tool calls: every Kanvil MCP `create_ticket` or `duplicate_ticket` call that has not failed is a reference, whatever the session later writes about it. T3 history omits tool output, so confirmation reads the full item through the `orchestration.getTurnItem` RPC and takes the created ticket ID from its result (Codex returns the result object; Claude returns it as JSON text in `content`). Older history pages are read with `view=activity` so tool calls are included. A call still running when its page is scanned stays pending and is read again after the usual wait without reporting an error; one that ends failed, cancelled or interrupted is dropped. An output without a ticket ID drops the reference; a failed read retries with the usual backoff. Message parsing below remains secondary evidence for tickets created another way.

Creation reports may announce a completed ticket batch, then list its tickets under Markdown section headings or in a Markdown table. The announcement only needs the creation verb and a ticket noun somewhere in the same affirmed sentence, so compound verbs such as "Created and verified six tickets:" qualify. The parser carries that affirmative context through the associated lists and tables, resets at ordinary prose or existing/related/next sections, and treats each list item independently so explanatory sentences do not suppress later entries. A table needs a Ticket, Issue or Key column and a header separator; only that column supplies references, so descriptive cells can mention existing tickets without collecting them. Explicit ranges and line-ending same-project numeric shorthand expand to at most 200 keys per expression. Future intent, negations, quoted/code content, illustrative tables without a creation introduction and unrelated mentions remain excluded; tracker workspace and creation-time checks still confirm every candidate.

`SessionThread.reportVersion` versions durable parser progress. A legacy eligible thread is walked again through the existing bounded cursor/backfill pipeline even when its timestamp is unchanged. The version and partial cursor survive failures and restarts; pending lookup retries, stored provenance, dismissal and consumption markers remain intact. No live database edits or dispatch replay are needed. `test/session-tickets.test.ts` covers sectioned/ranged reports, negative grammar, legacy recovery, failed pages, restart, idempotence and recovery into `status.json` while automation is paused.

Markdown headings form their own parser blocks even when their list immediately follows without a blank line. An affirmative batch introduction therefore carries through a foundation list and subsequent creation tables. Existing, related, example and not-filed sections still terminate that context.

Historical tracker task links keep their legacy ID as a separate reference kind. Confirmation uses the same explicit import provenance parser as state migration, matching source IDs or unambiguous source keys from workspace-scoped project snapshots and checking the original creation timestamp against the session/report lifetime. Native import timestamps and reused current numbers are not creation evidence. Snapshot reads are shared within the batch, invalidated by tracker revision changes, and respect its cancellation scope; malformed, ambiguous or unavailable provenance stays pending with backoff. Recovered rows keep native identity/status and original creation time, so completed tickets remain hidden. Migration preserves the parser version actually used rather than certifying old history as newly parsed.

Tracker key confirmation reads Kanvil's native project ticket endpoint; unscoped references resolve through `/api/v1/tickets/resolve`. Only HTTP 404 with the stable `not_found` code retires a missing creation reference. Other failures retain the reference for retry. Session-ticket metadata is invalidated immediately by Kanvil events, while conversation collection retains its bounded batches and durable provenance. Initial confirmation and ordinary refresh share revision-guarded publication so a concurrent event cannot be overwritten. Refresh resolves stable ticket IDs and updates current project, key and number together after a move, checking the workspace-scoped catalog before publication.

The shared tracker client distinguishes native `404 not_found` on task reads from other failures. Candidate confirmation discards those missing references for keys and task links. Refresh hides missing tickets and tickets whose project is absent from the active workspace catalog, including archived projects, without reporting a collection failure. It retains their history and last successful reading and retries with backoff so restored access or project membership can recover them. Streams and snapshots skip projects absent from that catalog; their ticket refresh bypasses cached metadata. Plain not-found text, malformed errors, authentication failures and outages remain retryable failures and preserve the last list. The page names the failed operation and cause rather than marking the whole list stale; the notification timestamp says Last failure because repeated failures replace the saved timestamp.

After every ordinary pass the service queues one background batch of `collectSessionTickets` (`src/session-tickets.ts`) behind any pending command, and queues another while the batch reports more work. A batch lists every top-level session T3 exposes (`T3.sessions`: settled and archived included, subagent and deleted threads excluded), reads changed sessions with `T3.conversation` (the bounded window, then older history pages by cursor, with items inherited from a forked thread dropped), confirms pending references with the tracker, refreshes listed tickets and marks consumed ones. Changed sessions and pending confirmations are processed newest-update first so recent reports precede historical replay. Both queues share the same comparator, including the timestamp of unfinished backfill. Each step is bounded (eight page reads, ten lookups, ten refreshes) so foreground commands never wait long.

Origin classification is stored as `upstreamReview` in the existing session scan record. Old records without a classification revisit their history through the same bounded backfill, even when the last-seen ordinal is already known. New candidate confirmation waits until the source is classified as ordinary. Existing rows and provenance survive unknown or failed reads; a confirmed review source is excluded by the shared projection rule. A missing continuation cursor is a retryable read failure, not proof of an ordinary origin.

Progress lives in the `session_threads` table: a session's `lastOrdinal` is the newest turn item processed, and an unfinished `backfill` holds the cursor of the next older page. A page's references are saved together with the cursor that follows it, so an interrupted read repeats the same page and never skips one; a failed read leaves the session's progress untouched and sets a five-minute retry deadline, so an outage neither loops on the same sessions nor starves the ones behind them. The first scan of a session walks history to its beginning; a later scan reads the window and, when the window no longer reaches `lastOrdinal`, walks back until it does. Unchanged sessions are not read.

A reference becomes a row in `session_tickets` only when the tracker returns the task in the configured workspace and the task's `createdAt` falls between the session's start and the report, so a ticket that is merely mentioned, or that predates the session, is not listed. A reference whose project the cached catalog does not know triggers one fresh catalog read per batch before it is dropped. A native `404 not_found` retires an unconfirmed reference. Other failed lookups stay pending with a growing retry delay, at most hourly. One task is one row whatever the number of reports; each report adds a source. Rows are refreshed from the tracker at most every five minutes. A native `404 not_found` on a saved ticket marks it missing and hides it from the actionable list without deleting its metadata or provenance. Missing rows are checked again after five minutes, including in realtime mode and after restart; a successful read restores the row with its current identity and status. Missing tickets do not fail collection. Other failed refreshes keep the old values, record the error and set the row's next read five minutes out, so an outage never loops on the same rows or starves the ones behind them. Failures, including a batch that cannot start because the configuration or the tracker client fails, are recorded as `sessionTickets.error` in status and never remove rows. Its `problems` group failed steps by kind and cause, each with a plain `title` and `cause` ("Couldn't confirm 3 reported tickets", "Kanvil live updates are reconnecting"), the affected ticket keys, IDs or session titles as `subjects` (at most 20), and the tracker's own wording as `raw` when it differs. The page does not show the problems itself: it shows "This list may be out of date" with a See issues button that opens the top bar's issue list; `message` joins the problems for logs and for errors saved before `problems` existed; the notice stays throughout retry backoff while any retained ticket row, reference, or still-listed session carries an unresolved failure, and clears once a batch finds none.

Dismissal (`t3-factory session-dismiss TASK_ID`, or the web page) sets `dismissedAt` on the row; the row remains so rescans, other sessions, refreshes and restarts cannot bring it back. A row is consumed when a Factory job for the task exists in any state other than a merely prepared or unknown dispatch, including runs started from the deck, the CLI, a chain or automation; the collector persists that as `consumed`. `writeStatus` publishes the remaining rows that are in their project's ready column (configured `readyStatuses`, else the first non-final column from the tracker), ordered by priority, project key and number, as `status.sessionTickets`. `test/session-tickets.test.ts` covers the service path, extraction, backfill and catch-up, interrupted reads, failed lookups, dismissal, consumption and membership with synthetic sessions and tracker answers.

Reconciliation and dispatch have independent workers. Completed-workspace maintenance coalesces its own sweep, performs one eligible job's guarded cleanup step, then schedules the next step without occupying an admission worker. Each job is visited once per sweep; intermediate steps resume on the next ordinary pass. Startup and fallback passes schedule maintenance even with automation paused, and a failed dispatch still schedules it. Pending cleanup snapshots and blocked-retry timestamps remain in the job record across restarts. Cleanup failures retain their existing error and backoff without changing the dispatch result.

Standalone manual dispatch also defers cleanup, leaving the durable job state for the next service pass or ordinary `once`. Standalone ordinary `once` and direct `reconcile` callers keep inline cleanup. Dry runs and `doctor` neither perform cleanup nor schedule a maintenance sweep. Deferred maintenance uses the same fresh-read checks, terminal and subagent handling, process checks, and guarded removal as inline cleanup.

Initial shell and provider reads overlap. The final validation phase independently re-reads the shell, forced selected-provider quota, native ticket with its full labels and server readiness, dependencies, and open pull requests. Ticket and relation promises are shared only within that phase. Dependency reads fan out with a limit of six, while cycle detection follows each ancestry path. A failed phase waits for all reads it started to settle before returning; artifact cache updates, policy decisions, durable ownership, and launch remain sequential. Inventory snapshots never substitute for these final checks.

A named-ticket dispatch resolves the requested identity directly, including its actual status. Dependencies outside that list reuse the live Kanvil snapshot or are resolved by ID with their complete native ticket metadata. Cross-project blockers, parent and child rules, final statuses, and inherited priority still apply. Dispatches without a ticket and the live queue continue to inventory every enabled project's ready columns; final pre-launch checks remain fresh.

### Chains

A manual dispatch of a ticket that waits on other tickets is not refused. The scheduler walks `blocks` relations, native parentId ancestry, and umbrella children through Kanvil (`blockerTree`) and answers `blocked-ticket-plan-required` with the whole tree. The caller then dispatches again with `--chain first`, which starts the highest-priority ticket in the tree that can start now, or `--chain all`, which stores a plan (`plans` table) and starts every runnable ticket within the run limits. Every pass advances active plans (`runPlans`), whether or not ticket automation is on: tickets start in priority order as the ones ahead of them finish in Kanvil, every launch still requires native automation readiness, and the target runs last. Only the launches made while the user chooses the chain carry manual policy; later continuations keep the automatic quota and idle policy, apply only the chain's recorded override, and use automatic models only when the chain was started with the automatic model. `t3-factory plan-cancel <id>` and `/api/plans/<id>/cancel` stop a plan; running tickets finish on their own. Active plans reach the page as `status.plans`.

### Journal

`Store.save` is the only job write path, so it records an event whenever a job is created, changes state, or gains a pull request. `Store.decide` records a check only when its outcome differs from the previous one or when it failed; a dispatch is journaled by the job it creates. Routine disabled checks update the latest decision without adding "Automation paused" events. Existing journal history is retained. Events live in the `events` table of `state.sqlite` (capped at 5000) and reach the page as `status.journal`; `/api/jobs/<id>/report` returns one run with its events and completion report. `t3-factory sources` (served as `/api/sources`) lists T3 projects, Kanvil projects with their native status categories, and project label catalogs so the projects page can pick instead of typing identifiers. `t3-factory job-stop <jobId>` asks T3 to stop a run's thread and the service reconciles at once; the web app's Stop button calls it through `/api/jobs/<id>/stop`.

## T3 compatibility

The integration uses application APIs that can change between T3 builds. Matching the T3 product name or having a provider signed in is not enough. The current client speaks T3 orchestration protocol v2 and requires:

- The `x-t3-orchestration-protocol: 2` header on every HTTP request, and `orchestrationProtocol=2` on the WebSocket URL.
- Authenticated HTTP snapshots from `/api/orchestration/shell` and `/api/orchestration/threads/<id>/bounded`.
- WebSocket tickets from `/api/auth/websocket-ticket` and the `/ws` endpoint.
- Effect RPC methods `server.probe`, `server.getConfig`, `server.refreshProviders`, `subscribeServerConfig`, `orchestration.subscribeShell`, `orchestration.launchThread`, `orchestration.dispatchCommand`, `vcs.removeWorktree`, `subscribeTerminalMetadata` (stream; the first event is a terminal snapshot), and `terminal.close`.
- The `terminal:read` scope on the scheduler credential for `subscribeTerminalMetadata`, and `terminal:operate` for `terminal.close`. Without `terminal:read`, workspace cleanup stops with `EnvironmentAuthorizationError`.
- Provider model metadata and usage windows with timestamps, remaining-window information, and reset times.
- Thread launch input and the public `run.interrupt` and `thread.pull-request.watch` commands compatible with the payloads in `src/clients.ts`.

T3 hosts that predate protocol negotiation (v1) are not supported. When T3 rejects the protocol header, the client reads `/.well-known/t3/environment` and reports `T3 orchestration protocol mismatch` with the version the server requires.

Stop is shared by operator requests, stalled-monitor recovery, and verified-completion monitor cleanup through `T3.stop`. It reads fresh bounded control state, interrupts the newest preparing, starting, running, or waiting run with `holdQueue: true`, or the latest settled run when provider background tasks or active background turn items remain. Queued runs, persistent dynamic tools, rolled-back items, and inactive provider rosters do not supply work to interrupt. With no owning run it disables visible linked PR watches; no work is a successful no-op. It uses the public RPC commands, never internal `thread.stop`, provider-session detachment, or queue resumption. Mutation failures propagate without retry; callers retain ownership until T3 confirms the outcome. Protocol fixtures validate emitted commands at the fake public RPC boundary.

Liveness comes from each v2 thread's `status` (its latest run), `activeRunId`, `pendingRuntimeRequest`, and `pendingBackgroundTasks`. Only a pending human-facing request, such as an approval or question, means the thread is waiting for a person. `dynamic_tool_call` and `auth_refresh` requests are internal work and retain execution capacity. A `waiting` status without a human-facing request also retains capacity until T3 settles the handoff, without adding a "needs you" event. Unknown request kinds remain human-facing. Background tasks of kind `monitor`, including pull request watches, are passive monitoring, and kind `command` is a local process; any other kind, including unknown kinds, is active worker execution. An active run whose provider sessions are all `stopped` or `error`, on a thread unchanged for 30 minutes, is orphaned and does not count as executing. Human-facing requests and fresh runs are excluded from the probe; old internal requests and requestless waiting runs remain eligible. Detection reads `runs` and `providerSessions` from `/api/orchestration/threads/<id>/bounded`; a failed or ambiguous read keeps the run executing.

Dispatch launches a thread over RPC with a `worktree` workspace strategy. T3 creates the worktree from the project's workspace root, which must match the configured `repoPath`, and runs the project's setup script. The plain HTTP dispatcher does not prepare worktrees. The scheduler validates the fields it consumes and stops affected dispatches when the contract is incompatible. It does not edit T3's database or fall back to driving its UI.

The persistent service multiplexes shell and provider feeds with RPC calls on one connected socket. Shell snapshots and sequenced entity changes replace repeated whole-shell HTTP reads; multiple entity changes may share a sequence. Snapshots marked with `resolvedRepositoryIdentityRoots` are partial project enrichment: merge their projects without replacing threads, removing unrelated projects or advancing the application cursor. Disconnects, incompatible events and credential changes invalidate the affected projection. Cold or disconnected reads use the authoritative snapshot path. Old-run orphan detection stays in bounded background batches; an unconfirmed run remains busy.

Connected shell reads share immutable entities instead of repeatedly deep-copying the complete shell on the service event loop. Updates replace the affected entity and array, preserving snapshots already held by other readers. Callers that need to edit a thread must copy it first, as workspace cleanup already does. Orphan annotations produce a new reader view without mutating the authoritative feed.

Ticket references are indexed once per immutable shell snapshot and grouped by project. Inventory and final duplicate checks use the same matcher and index. Mutable inputs retain the per-thread predicate, whose text cache invalidates when title or branch changes. Case, digit boundaries, overlapping keys, leading zeros and subagent exclusion preserve the existing matching contract. Weak caches do not retain retired snapshots.

Repository reads start on the next event-loop turn, allowing already-queued requests to share a capture that has not begun. Their timestamp records the actual capture start; a fresh caller arriving afterward gets a new read. This removes redundant subprocess starts without accepting an older snapshot. Immediately before reservation, the scheduler also reads the current trusted T3 projection synchronously, invalidates inactive-thread proofs changed during network reads, and checks the selected project mapping. Lost projection trust forces an authoritative fallback pass. Invalid stream data clears trust before error observers can consume it.

Unnamed service starts use the background inventory's Up next rows as selection hints. Standalone CLI passes rebuild inventory because they have no background refresher. Before reservation, the shared dispatch boundary checks the selected ticket's current native readiness, difficulty, blockers and children, tracker generations, repository branches, open PRs, T3 ownership, current configuration, allowance and shared limits. Stale hints are skipped without rebuilding every project's inventory. Concurrent manual starts take distinct ticket preparation leases; unrelated tickets share no preparation lock. Dry runs reach this same boundary but create no reservation or launch.

In the running service, only the inventory lane publishes Up next. Admission lanes may inspect empty or scoped queues and must not replace the shared catalogue with them. Standalone CLI passes publish their own complete inventory.

Label occupancy is computed once for each synchronous assignment selection, including planned starts, and refreshed after asynchronous work. The final reservation boundary still checks current jobs and thread state. Candidate filtering must not reload the ledger or scan all threads for each ticket. Ticket matching reuses a bounded cache of case-insensitive expressions; branch checks with no released history match the original ref text directly.

Manual preparation leases also reserve their hinted labels for selection, so simultaneous unnamed starts can choose other available work instead of colliding on the last label slot. This advisory occupancy transfers to the durable job without an asynchronous gap and clears on failure, dry run or cancellation. The final gate still uses authoritative ticket labels and current durable jobs.

For GitHub.com, the running service keeps an authenticated HTTP client for fresh PR inventory instead of spawning `gh pr list` on each start. It obtains the existing CLI credential lazily with `gh auth token --hostname github.com`, keeps it in memory and refreshes once on HTTP 401. Every query reads current PRs, including full bodies and branch names, follows pagination, and fails closed on errors, invalid cursors or more than 1,000 open PRs. It does not use the eventually indexed search API. A custom `GH_HOST` and standalone commands retain the CLI path. Service shutdown aborts these read-only requests; cancelling one consumer does not cancel a sibling's shared authentication. GitHub's [authentication](https://cli.github.com/manual/gh_auth_token) and [pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api) contracts define the wire behavior. Kanvil relations and child pagination begin concurrently once the selected ticket's identity is known; both must settle before validation proceeds.

Connected provider snapshots may authorize a start within the configured quota age, provided they postdate the reservations already known when preparation began. Concurrent preparations can use the same allowance snapshot; each synchronously reevaluates the latest connected allowance immediately before reservation. An exhaustion update blocks submission. A later preparation accounts for prior reservations and refreshes when needed. Cold or stale quota refreshes target `server.refreshProviders({ instanceId, workspaceSnapshotsOnDemand: true })` and consume its compact reply. Do not set `refreshModels`: on the supported T3 build it enters globally serialized manifest refresh and model rediscovery. Targeted refresh already refreshes usage; timestamps and quota validation remain authoritative, and two failed probes block the run.

RPC preflight uses the cheap `server.probe` handshake and checks physical socket state before reservation. A pre-open socket failure can acquire one fresh ticket and connection before submission. The Effect transport never reconnects itself with a consumed ticket URL. Submitted mutations are never replayed, and shutdown retains ownership until accepted calls settle. `test/native-rpc.test.ts` exercises rejected upgrades, the native open timeout and a dropped mutation reply over a real local WebSocket. Local fixtures prove these boundaries, not the cause of a historical T3 server stall. Deployment validation must measure request receipt to native thread creation separately from model startup; a withheld-launch benchmark proves only the selected-ticket preparation path.

Run `doctor` against your actual T3 build before enabling automatic work. Live verification requires your own credentials and configured projects; keep those outside tracked files.

Command tasks do not count as provider execution or extend personal activity. Their unfinished running jobs still retain automatic-run reservations in `busyProviders`, because command notifications can resume them without another admission check. Verified completion and human-input waits release those reservations. A settled turn that yields to pending commands without a report is an unfinished background wait (`commandWait` in `src/policy.ts`): the commands' completion notification resumes the same job, so reconciliation keeps it `running` with reason `Waiting for background commands`, journals no "needs you", and retains its claim and workspace. A missing report authorizes no Stop, cleanup or redispatch. An awaiting-human report written before the job resumed from waiting, or before the latest user message, has been answered and does not describe the wait; the job records `resumedAt` when it sees that resume. Any other report goes through the usual verifier: valid complete or no-work reports finish the job despite leftover commands, explicit awaiting-human reports wait for a person, and invalid, mismatched or unverifiable reports keep their diagnostic. Stopped and orphaned runs, and a turn whose command roster has emptied without a report, still surface the missing-report diagnostic. Human requests, runtime handoffs and non-command workers retain their existing protection. Passive monitors still use the monitoring timeout; a mixed monitor/command roster never authorizes timeout cancellation.

Command cleanup extends the existing workspace-maintenance step and T3 stop helper. It validates the job report through the same completion verifier as reconciliation, including Done and merged delivery evidence even when a dismissed job's commands have already exited, then checks a fresh bounded projection and shell before interruption. Queued runs, pending requests, new user messages, non-command turn items or provider tasks, active subagents, changed ownership, shared bindings, and changed Git/report evidence hold cleanup. Persisted todo-list items are passive plan display, so their item status alone does not block verified cleanup. User messages after the report was written hold cleanup even when a dismissed job is only now being verified. The job's durable `commandStop` distinguishes requested, uncertain and confirmed outcomes. A request is saved before dispatch and is not resent while commands remain, including after restart. Confirmation requires a later empty roster; terminal and process-CWD guards still apply before removal. Tests in `policy`, `monitor`, `workspace-cleanup`, and `service` use isolated fixtures, including deferred Stop and injected races.

Completed-workspace cleanup closes the completed thread's idle T3 terminals with `terminal.close`, always passing `terminalId` and `deleteHistory: false`. It never closes a terminal that is starting or running a command, or one owned by another thread. It also requires `lsof` to verify process working directories. If the terminal snapshot or that check is unavailable or fails, the workspace is preserved. Removal uses `force: false`; workspace metadata updates use the expected worktree path to prevent changing a different binding.

### Cleanup management

`src/workspace.ts` is the shared filesystem inspection and removal boundary for automatic cleanup and operator actions. Its indexing and projection loops yield after bounded batches so deadline and cancellation events can run. Review and removal always read fresh identity. It adds cross-job inventory, read-only evidence, expiring force reviews and durable operator action records. Normal cleanup may discard all ignored files after verified completion, merged HEAD and fresh idle/activity checks. The shared removal boundary rechecks identity and tracked/untracked contents after its final activity callback, then uses the T3 force flag only when ignored files require it. Explicit deletion review can override completion/content holds, but not live safety checks. Git status summarizes matching ignored directories instead of expanding dependency files. Review fingerprints skip disposable ignored contents; their total size stays unknown when that traversal is skipped.

Every row has one fixed height: name, project, a state `Tag`, a `Help` glyph whose tooltip carries the blocker and the last failed attempt, age, and one icon-only action in the queue's `next-run` style whose label names the verb and folder; progress (Queued, Deleting…) replaces that icon with a spinner. Details expand immediately from inventory data; Check and Delete anyway run inline on request. The force request still carries the reviewed folder name as its confirmation. Delete N selected reviews each selected Blocked row and forces it after one confirmation that names how many will lose work. Bulk deletion sends one saved operation per worktree, in order, through the existing drain, so each row settles as soon as its own request returns. A completed request reports the durable per-target outcome rather than treating exit code zero as removal. Failed attempts retain their per-worktree result after refresh; confirmed removal requires verified physical absence. Saved outcomes overlay older inventory until its result snapshot catches up; `/cleanup` needs its own view because its inventory includes worktrees without any Factory run.

Cleanup shows one worktree list and one Delete action: Delete N unused, or Delete N selected once rows are picked. Manual deletion checks each candidate against the current remote release tip and deletes only merged, idle worktrees without tracked or untracked changes, regardless of Factory ownership. The merge check accepts ancestry or a squash merge: the branch's tree committed once onto its merge base must share a patch-id with a commit on the release branch (`released` in `src/scheduler.ts`), and the remote tip is fetched when it is not yet local. T3 leaves idle setup shells open in worktrees; like automatic maintenance, manual deletion closes terminals that have no running subprocess and inspects again before removing. Cleanup discovery and page projection are separate. The scheduler coalesces `Store.save`/`saveCleanupAction` notifications into a background catalog refresh, with normal passes covering worktrees created outside Factory. The persisted catalog is scoped to repository and T3 mappings and survives restart. Web reads use the existing store directly, and control inventory reads use the catalog directly; both apply cheap job summaries and durable per-path outcomes before filtering/pagination. The hot path does not read historical dispatch prompts, scan Git or call T3. Cold/explicit refresh uses its independent catalog worker, or the existing exclusive offline CLI when the scheduler is absent. Catalog publication reuses status notifications to update an open page. `/test/browser/cleanup.html?run=1&catalog=1` checks background publication, retained content during refresh, and no scan/cancellation session for cached reads.

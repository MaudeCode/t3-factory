# Running the factory

The CLI works from source as `node src/main.ts COMMAND`, or as `t3-factory COMMAND` after installation. The web page calls the same backend.

## Common commands

| Command | Effect |
| --- | --- |
| `status` | Prints the current status, read from the local ledger. |
| `doctor` | Checks live integrations and reports a possible decision without dispatching. With `triage` configured, it also runs the triage sandbox canary and exits non-zero unless the CLI refuses both probes. |
| `once --dry-run` | Previews a cycle using the current enabled state and policy. |
| `pause` / `resume` | Disables or enables new automatic ticket and discovery work. |
| `queue-pause` / `queue-resume` | Holds or releases what you queued: runs waiting for a slot, chains and Epic runs. Held rows stay queued. Running jobs continue. |
| `upstream-pause` / `upstream-resume` | Disables or enables new upstream release reviews, independently of `pause` / `resume`. |
| `repair-pause` / `repair-resume` | Disables or enables new CI repairs, independently of the other switches. Works on a config file with no `repair` section. A running repair continues. |
| `triage-pause` / `triage-resume` | Disables or enables new inbox triage runs, independently of the other switches. A running report finishes. |
| `triage-run` | Asks the running scheduler to triage now, past the triage switch and the quota reserve; an actionable report goes on to promotion past the same limits. Concurrency, an exhausted allowance and promotion limits still apply. |
| `triage-retry TICKET_ID [--override-limits]` / `triage-promote TICKET_ID [--override-limits]` / `triage-close TICKET_ID` | The owner's decision on one open inbox report, by its tracker ticket ID, through the running scheduler. With `--override-limits`, the pass a retry or promote starts is forced like `triage-run`, so the report reaches its ticket past the triage switch and the quota reserve. Retry clears the report's triage and promotion labels so the next pass triages it again; promote does the same and records the owner's approval of that report text in the scheduler's state, so that pass makes a ticket of it; close cancels it. A ticket that is not an open report in a configured inbox is refused. |
| `ticket KEY` | Print one ticket as the web app's ticket panel shows it: an allowlisted, read-only view from the tracker |
| `run` | Runs the scheduler continuously. |
| `model-catalog` | Reads the models and options advertised by T3. |
| `config-get` | Prints validated scheduler configuration. |
| `config-save` | Reads `{ "base": ..., "config": ... }` on stdin; rejects stale edits and preserves JSONC comments where possible. |

### Scheduled on and off

The web app's Settings, Limits tab, has a Schedule with two one-shot timers: Turn on at a time, and Turn off at a time or at a provider's weekly reset. Each timer sets Automation and the Queued switch together, once, and clears itself. The Automation switch and the Queue page's Queued section show the next one. Running jobs finish.

To use up an allowance before it resets, queue what you want run or turn Automation on, set Turn off to Weekly reset, pick the provider and save. The weekly reserve already relaxes to its floor as the reset nears, so lower the floor on the same tab to spend the last of it. At the reset, or earlier if the provider resets early, automatic starts stop and queued rows are held, so the next week's allowance is left alone. Release the queue with its switch or `queue-resume`. The timers are `schedule` in the [configuration](configuration.md).

## Manual runs

```sh
t3-factory dispatch --ticket APP-123 --model default-model --dry-run
t3-factory dispatch --ticket APP-123 --model default-model
t3-factory dispatch --override-limits
t3-factory dispatch --override labels
```

Use your own ticket key and configured model ID. With `--model auto`, `--provider codex` or `--provider claudeAgent` restricts selection to that provider and also permits its manual-only presets. Add `--override-limits` to intentionally exceed scheduler thresholds. A provider choice cannot be combined with an explicit model ID. Omitting the ticket selects the next eligible one. `--model auto` selects from eligible automatic presets; an explicit model ID can select a manual-only preset. Manual dispatch starts ticket work, never discovery.

Manual jobs can overlap other runs and can start while automatic dispatch is paused. `--override-limits` skips the scheduler's idle-time, quota-reserve, label-limit and provider-limit thresholds for that run. `--override` skips only the ones you list, comma-separated from `idle`, `reserve`, `labels` and `providers`; for example, `--override idle,reserve` starts now but still waits for a free label slot. The web start bar offers the same four choices, all on by default. Without the provider override, manual starts respect provider run limits, including zero. Auto selects from providers with capacity; an explicitly chosen model is refused when its provider has no capacity. The override cannot select a model whose applicable allowance is exhausted, even when the override is enabled. Automatic model selection skips exhausted presets and tries the next eligible model. It does not bypass provider-enforced limits, difficulty ceilings, readiness, dependencies, duplicate ownership, or merge gates. Manual Codex runs already omit the scheduler's idle and reserve checks; they still require valid provider quota information.

### Tickets held back by earlier work

The scheduler holds a ready ticket back when earlier work still references it: a T3 thread or branch, a Git branch, an open pull request, or a finished run whose work it cannot verify. In the Queue's Held back list and on the ticket panel's held line, such a ticket has an icon-only **Investigate in T3** button (a magnifier). Other held reasons have none. After a confirmation it starts a reconcile run, the same request as:

```sh
t3-factory dispatch --reconcile APP-123 --model auto
```

The web app sends it to `POST /api/tickets/<key>/reconcile`, and its progress shows in Operations like any start. A reconcile run is refused when the ticket is not held back by earlier work, or when any run for it is still open. It goes through the same model selection, quota, provider-limit, label-limit and override choices as a manual start. A request that a limit holds is refused, never queued, because a queued start would pick whichever other ticket is ready. Like upstream reviews and CI repairs, it does not wait for provider idle time.

The run starts in a new thread titled `Factory reconcile: <TICKET>`, on a `chore/factory-reconcile-<id>` branch. Its prompt, [`prompts/reconcile.md`](../prompts/reconcile.md), carries the threads, refs and open pull request the scheduler found, and the configured delivery workflow. The run takes one of four outcomes:

- Work already merged on the release branch: it records the evidence, closes the ticket in a done status, deletes merged clean branches and worktrees and archives stale threads, then reports `no-work`.
- An unmerged branch or open pull request with real work: it delivers it through the delivery workflow with every gate unchanged and reports `complete` with the merged pull request, verified like a ticket run.
- Abandoned or superseded leftovers: it records why on the ticket, removes clean local branches and worktrees and archives the threads, and reports `no-work`. The ticket stays open and becomes eligible again: the queue skips archived threads, while a settled thread whose worktree is gone still holds the ticket back.
- A session still active on the ticket: it touches nothing and reports `awaiting-human`.

It deletes a local branch or worktree only when it is clean and its head is merged or its work is recorded on the ticket, and never force-deletes a remote branch or closes a pull request without recording why on the ticket. A `no-work` report needs the run's own worktree clean at its creation commit, like a ticket closed without delivery, but may leave the ticket open.

### Epics

```sh
t3-factory dispatch --epic EPIC_ID --model auto --override labels
t3-factory plan-cancel PLAN_ID
t3-factory plan-override PLAN_ID --override reserve,labels
t3-factory plan-order PLAN_ID PLAN_ID
```

`plan-override`, or `/api/plans/<id>/overrides` with `{ "overrideLimits": [...] }`, replaces the limits a running Epic or chain overrides. Its next launches use them; `--override-limits` is every limit and no flag respects them all. Tickets already running are not touched.

`plan-order`, or `/api/plans/order` with `{ "ids": [...] }`, sets which queued runs, chains and running Epics are offered free slots first: the named plans in the order given, then any other active plan. Queue's Queued section sends it when a row is dragged. A plan started later joins the end.

`--epic`, or `epic` on `/api/dispatch`, starts a Kanvil Epic with one model, provider and override choice. It cannot be combined with `--ticket`, `--chain` or `--upstream`. Every ticket that can start does, within the limits you did not override, and the rest start as their blockers finish. A blocker outside the Epic joins the run and is marked as outside. Native readiness, holds, hard allowance, duplicate checks and merge gates still apply to each launch.

A start is refused, and no run is created, when the Epic is archived, already running or has no unfinished tickets, when an unfinished ticket or blocker is in a project missing from the Factory config or disabled, when the Epic has tickets in projects Factory cannot read, or when an unfinished ticket or blocker is on hold or has automation readiness off. A held parent ticket with unfinished children is the one exception, because its children carry the work: they run, the parent does not, and the Epic stays open until you close the parent. Overrides never waive these, and pausing automatic runs is not a reason: you can still send an Epic while they are off. If a ticket loses readiness after the Epic starts, it waits and the rest continue. `status.epics` reports the same answer for each open Epic.

A running Epic rereads its members on every pass: tickets added to it join, and removed tickets that have no run leave. A cancelled ticket counts as finished. It ends when every remaining ticket is finished and none are hidden from Factory. Hidden tickets keep it active, and a failed read keeps its last list and shows the error on its tickets. A ticket whose project leaves Factory mid-run does not start and its dependents wait, while other tickets continue, until it is finished elsewhere, the project returns or you cancel. Archiving an Epic does not stop a running one. Cancelling lets running tickets finish.

Automatic starts never take a ticket from a running Epic. Set `holdEpicTicketsUntilStarted` to also keep them off an Epic you have not started yet. Starting one ticket by name always works.

The **Epics** view of the web app's Queue page does the same from the browser. Each Epic is one collapsed row: its title, a state (Ready, Can't start, Running, Needs you, Done or Cancelled), its progress and what its runs are doing, and its controls. An alert symbol on the row means the Epic cannot start. Select the row to read the reason and list its tickets with their state and what they wait for. A search or filter that narrows to particular tickets opens the Epics it matches until you clear it. Select a ticket to open it. Set the page's provider and override controls, then press Run; the model is chosen automatically. An Epic that cannot start has Run disabled, and its reason names the projects to add or enable, the tickets to fix, or how many tickets Factory cannot read; overrides do not change this. It updates by itself when the cause clears. A running Epic shows its recorded model and overrides, any hidden tickets keeping it open, and Cancel Epic. Each Epic appears once: an Epic run again after a cancelled run shows only the later run. Epics that finished in the last day are listed with their final state in a Finished group, collapsed until you open it or search or filter. Running Epics appear only on this tab, not among the chains on the deck or Up next; their tickets' runs still appear with every other run.

## Session tickets

The **Sessions** view of the web app's Queue page lists tickets that your T3 sessions reported creating, whichever project they belong to. The scheduler reads every top-level session's conversation in the background, including older history and sessions that are settled, confirms each reported ticket with the tracker, and keeps the list in its state database, so it survives restarts and needs no skill run or reporting thread. A ticket appears only if the tracker shows it was created during the session that reported it; mentions, quoted text, tables and examples do not count. The list is not the automatic queue: it is every open session-created ticket in a ready column, including ones that have automation disabled or belong to a project the factory does not run. Tickets in progress, in review or done are hidden, and return if they move back to a ready column.

Run starts the ticket through the shared **Run now** path, with the model chosen at dispatch. The header's Auto / Codex / Claude icon selector chooses the provider. Auto applies the four override toggles; choosing Codex or Claude forces that provider, selects its highest-priority configured model accepting the ticket, and overrides all scheduler thresholds. The limit toggles are disabled until you return to Auto, which restores your previous selections. The four icon toggles select which limits to override for individual and bulk starts: idle time, quota reserve, label limits and provider limits. Highlighted icons mean override; their names and pressed states are available to assistive technology. Provider limits are respected by default, so a provider set to Off cannot receive these starts. The other three overrides default on. Choices are saved in this browser and captured when each request is queued, including chain choices and retries. Readiness, dependencies, hard quota, duplicate ownership and merge gates still apply. The entry leaves the list once Factory confirms the run started, whether from this page, the deck, the CLI, a chain or automatic scheduling; a refused or failed start keeps the entry and its outcome. A start that has to wait, shown under Queue as a queued run, also takes the entry off the list; cancelling the queued run lists it again. Remove takes the entry off the list for good without touching the ticket, its runs or scheduling; `t3-factory session-dismiss TASK_ID` does the same. A collection failure adds a count to the connection indicator in the top bar; click it, or See issues on the page, for one line per problem with the affected ticket IDs under Details. The last known list stays visible and collection retries automatically.

## Automatic scheduling

Tickets matching a project's `priorityLabels` are considered first, in configured rank order, followed by unmatched tickets; labels listed together share one rank. Within each rank, urgency orders tickets: urgent, high, medium, low, then no priority. Within an urgency tier, the highest-ranked available model with a sufficient difficulty ceiling gets first choice. Project ticket counts, rotating ties, and oldest-ticket order break remaining ties. Without configured priority labels, the existing urgency ordering applies. A ticket whose project `labelLimits` entry is already full is passed over for the next ticket that fits; when nothing else fits, the provider shows `label limits are full`.

Prerequisites inherit the highest scheduling priority of unfinished tickets they unblock through Kanvil `blocks` relations, including dependency chains across enabled projects. Label rank and urgency are compared together using the same ordering as ticket selection. For example, if an urgent first-ranked compatibility ticket depends on an ordinary low-priority ticket, the prerequisite is scheduled in the compatibility/urgent tier. Tracker fields are unchanged. Completed dependents and disabled projects contribute no priority, and removing a dependency clears its effect on the next inventory. A prerequisite still needs its own readiness and difficulty labels and must be unblocked; inheritance never starts the blocked dependent early.

Claude and Codex have separate simultaneous-run limits, configured under Automation. Each defaults to one. Set either limit to zero to turn off automatic starts for that provider, including discovery; manual starts can exceed the limit only with the provider override. Active factory runs, including manual runs, count toward the limit for new automatic starts. Waiting runs free capacity. Lowering a limit holds new starts until there is room; it does not stop running work. Each stream checks that provider's personal activity in T3. Scheduler prompts do not count as personal activity; user replies do. Local commands, tests, and PR waits consume no provider turn and do not keep extending the idle timer. A child-agent marker is resolved against its live thread: a stale idle child cannot keep a completed parent active. Live or unresolved workers remain protected; native idle children without a run lifecycle retain protection while the parent or child has changed within the monitoring timeout. The idle clock retains actual messages, human responses, and completion times. The factory does not track usage outside T3.

List non-Factory workflows that run autonomously in `t3.autonomousThreadIds`. Their activity and linked child tasks are excluded from the personal-idle gate, even while executing. This does not waive subscription quota checks or change Factory run limits. Changing the list rebuilds the personal-activity clock so an excluded workflow cannot leave a stale blocker behind.

A job waiting for human input releases its provider slot. Active turns and background workers keep it. Parked jobs are unlimited unless `maxWaitingPRs` sets a cap. A factory-owned passive monitor that exceeds the configured timeout is stopped and confirmed inactive before being parked. Personal sessions are never stopped by this rule.

Dispatched jobs use T3's native `link_pull_request`, `watch_pull_request`, and `unwatch_pull_request` tools for PR registration and CI/review waits. The shared prompt requires agents, including Opus, to start the native watch and end their turn instead of running shell watchers or polling loops, even when the supplied delivery skill recommends polling. A notification resumes the same job; the agent must still verify current-head CI, review and approval proof before merging. Missing or failing native tools are reported as integration blockers. Prompt changes apply to newly dispatched jobs after installing the updated Factory source; existing threads retain their original instructions.

Upstream release reviews run ahead of ticket work, through the same quota and run-limit gates, but they do not wait for provider idle time. They start only while `upstream.enabled` is true, whether ticket automation is on or paused; the web app's Sources page (Upstream releases view) has the switch and also shows each watched repository's reviewed and latest releases and the review runs. The scheduler reads each watched repository's releases with `gh` at most every `checkMinutes` (the upstream's own, else `upstream.checkMinutes`), excluding drafts, and pre-releases unless the upstream allows them, before the listing limit. In the same read, one GitHub GraphQL query compares each listed release with the last reviewed one by the commits they resolve to. The candidate is the newest published release that strictly descends from the reviewed one; a release at the same commit, behind it, or diverged from it is never a candidate, whenever it was published. A diverged release that would have been newer than the candidate, or a failed comparison, shows as the repository's check error; a failed read never adds a candidate. The scheduler caches the verified range for its base, and dry runs and Review now read only that cache. When a candidate exists, it starts one review thread, titled `Upstream review: <name> <base>..<candidate>`, in its own worktree, and the prompt names both commits. Nothing else is started, and no model runs, while a repository has no new release. A verified `complete` report with created tickets, or a `no-work` report, records the candidate as reviewed in the scheduler database, and it becomes the next review's base. A review that covered a different range reports it as `range` with the same base; the base moves to that candidate only when GitHub confirms it descends from the base. A review dispatched before ranges were verified is compared at completion, and a backward or diverged range completes without moving the base. An awaiting-human or unverified report leaves the record unchanged, and that repository is not read again until its review finishes. A candidate is never dispatched twice, including after its review is dismissed by settling the thread.

CI repairs follow the same path ahead of ticket work and upstream reviews, through the same quota and run-limit gates, without waiting for provider idle time. They start only while `repair.enabled` is true; the switch is on the web app's Settings page (Repair tab), which also shows each watched workflow's newest result, the run being followed, the last repair, the cooldown, and the repair runs. Every scheduler pass starts by reading each watched workflow whose newest run on the base branch is queued or in progress, at most every 15 seconds, so a failure starts its repair on the first pass after the run ends. A pass also reads each watched workflow of a project after one of the scheduler's own pull requests in that project is verified merged, and when a cooldown has just ended; otherwise it reads every `repair.checkMinutes`, to notice merges the scheduler did not make. A failed run starts one repair thread, titled `CI repair: <project> <workflow> run <id>`, on a `fix/factory-repair-<id>` branch in its own worktree. The prompt carries the configured delivery workflow (`factorySkill`), whose pull request, validation, CI, review, merge and Hold gates apply to the repair pull request; its ticket steps do not. Its report names the failed jobs it repaired and those it left, and its pull requests must be verified merged into the base branch before it is complete. A report that leaves a job unrepaired must list the ticket that records it in `createdTaskIds`; without one the job waits instead of completing. See [configuration](configuration.md#ci-repairs) for the rules that hold a failed run back.

Discovery runs only when there are no eligible tickets and no otherwise-ready tickets waiting for difficulty classification. It uses an available automatic model and a separate task and worktree. A no-work result starts the project's configured discovery cooldown.

To send a review yourself, use **Review now** beside a repository marked **review due**, or `t3-factory dispatch --upstream owner/repo --model auto --override-limits`. This explicit action works with automatic reviews paused. It uses the cached due release for that enabled watch, keeps hard allowance and duplicate checks, and never starts unrelated work. Omit `--override-limits` to retain ordinary manual threshold checks. A review target cannot be combined with ticket, readiness-waiver or chain options.

## Completion and recovery

A delivered ticket is complete only after its report, Kanvil Done status, and merged PR evidence agree. A model turn ending or a PR opening is not completion. Failed starts and unexplained endings park for inspection instead of triggering blind retries. T3 can leave a run active after its provider sessions stopped. When every session has been `stopped` or `error` and the thread is unchanged for 30 minutes, the scheduler treats the run as ended: it reads the report, or parks the job, and releases the execution slot. It never stops that run, and it preserves the workspace while T3 still reports the run active.

A ticket run can also verify that no change is needed because the ticket is already delivered, superseded or a duplicate. It records the evidence on the ticket, closes it in a configured final status, and reports `no-work` (or `complete`) with no PR URLs. A held, unverified or not-ready ticket remains unfinished. The worker presents the concrete question in its own thread, keeps its job `awaiting-human`, and resumes after the answer. It never ends or settles its job because operator input is needed. The scheduler accepts this closed-without-delivery outcome only when both conditions hold:

- The ticket is closed in a configured done status or `cancelled`, which covers a duplicate or superseded ticket and one the owner cancelled whatever `doneStatuses` lists. Disabling automation, archiving an open ticket, moving it out of the ready statuses or adding a hold does not finish its job.
- No undelivered work exists: the workspace is clean and still on its assigned branch, and both the branch and the checkout are back at the commit the branch was created at, which must already be part of the release branch. A run may commit scratch work, such as temporary diagnostics, and reset it away, but no commit in the branch's or checkout's Git reflog other than the creation commit may be part of the release branch. A commit pushed straight to the release branch therefore still blocks completion. If the assigned branch or its reflog no longer exists, nothing can be verified and the job also stays parked. Otherwise the job stays parked until the work is delivered through a PR or the agent asks for input.

After verified completion, the scheduler automatically removes the assigned workspace. It closes passive monitors, detaches the idle T3 workspace binding, closes the completed thread's idle T3 terminals, and removes the Git worktree through T3. Ignored files are disposable once completion, merged HEAD and idle ownership are verified. It rechecks the assigned workspace, merged branch and head, ticket status, thread activity, shared workspace references, and running process working directories. Subagent threads descended from the job thread belong to its workspace: once they are idle, their passive monitors are closed and their bindings are detached first. Tracked changes, untracked files, unmerged, resumed, or active work are preserved, as is a workspace shared with any other thread or one whose T3 terminal is still running a command or that any other process still uses. A merged PR verifies the workspace when its head branch matches or its head commit equals the local branch tip, so a branch pushed under another name still counts. When the workspace directory is already gone and Git no longer registers it, cleanup only detaches the binding. Cleanup retries safely after a failure, about every 15 minutes while it stays blocked, retains the conversation and completion history, and never runs during diagnostics or dry runs. Discovery workspaces and tickets closed without delivery are eligible only when their clean head is already part of the release branch.

Local command tasks consume no provider turn, but their unfinished running jobs retain automatic-run reservations until verified completion or a human-input wait. While an unfinished run waits for its own background commands, such as a long validation suite, it stays running with "Waiting for background commands" and does not appear under Needs you; the command's completion resumes it automatically, and its claim and workspace stay in place. An awaiting-human report that was already answered does not bring it back; any other report is processed as usual. A stopped or orphaned run, or one whose commands have finished without a report, waits with the missing-report diagnostic. Settling the thread does not bypass completion checks or discard an operator wait.

For verified finished jobs, including dismissed jobs with a valid completion report, workspace maintenance automatically requests Stop for leftover command-only work. Ticket delivery must be Done and merged. Settling alone or command age cannot authorize Stop. Fresh T3 and bounded-state checks preserve queued follow-ups, resumed user work, pending requests, workers, active descendants, changed ownership and shared workspaces. Missing reports, awaiting-human reports and uncertain evidence retain the workspace with `workspaceCleanupError` and its retry timestamp.

The durable job field `commandStop` records `requested`, `uncertain`, or `confirmed`, with request and confirmation timestamps and any transport error. Stop acceptance does not confirm process exit. Maintenance rechecks T3 after the request and across restarts, and never resends an unconfirmed request automatically. If commands remain after a rejected or uncertain Stop, inspect the thread before using the existing manual Stop operation. Once T3 reports no pending commands, the normal terminal, process-CWD and Git checks resume. A live process still prevents removal.

Each ticket run works on a branch named `<kind>/<TICKET>-factory-<id>`, where the kind comes from the ticket's kind label in conventional-commit terms: `bug` and `sec` give `fix`, `feat` and `ux` give `feat`, and `perf`, `test`, `ci`, `docs`, and `chore` keep their names; a ticket without a kind label gets `chore`. Discovery, upstream review and reconcile branches stay under `chore/`; repair branches are `fix/factory-repair-<id>`.

Completed jobs retain history but release their live ticket claim. Reopened tickets can run again when historical tasks are inactive and unchanged, and historical branch tips still match verified merged PRs or, for tickets closed without delivery, are still untouched at a commit that is part of the release branch. New work and open PRs continue to block duplicates.

Thread title and branch references block tickets only within the ticket's configured T3 project. Subagent threads never do: they share their parent's worktree and branch, and their titles often name tickets they only read or redrafted. An explicitly settled thread outside Factory does not reserve the ticket when its worktree is present, clean, still on its assigned branch, and both branch and checkout histories have stayed at their creation commit on the release branch. Active runs, pending requests, background tasks, shared branches or workspaces, missing Git evidence, and open PRs retain duplicate protection. Thread and open-PR checks run again immediately before launch.

The scheduler records a dispatch before submitting it to T3. Restarting reconciles the recorded task IDs. Uncertain submissions are not replaced with new tasks automatically. Web dispatches also use persistent request IDs, so repeated taps cannot create a second accepted request.

Explicitly settling an inactive factory task in T3 dismisses it from the factory view only after its report and completion evidence verify, with no pending operator request. An unfinished ticket, missing report or operator wait keeps the job under Needs you even if its thread was settled. Workers remain isolated to their assigned job and worktree; only an explicit user instruction authorizes messaging or managing another session. Deleting a factory thread in T3 still dismisses its run once T3 no longer lists the thread, archived threads included, and frees its run and label slots. A thread T3 never showed keeps its slot as an uncertain launch.

A verified finished run leaves the T3 list on its own, whatever its kind and whether or not it merged a pull request: once its workspace is cleaned up, the scheduler asks T3 to settle the thread automatically. T3 refuses if the thread changed since the scheduler looked or you set its state yourself, and the scheduler leaves pinned threads and threads with automatic settlement turned off alone. A run whose workspace cleanup is refused, for example because it holds local changes, stays in the list. Ticket runs that merge a pull request are usually settled earlier by T3's own settle-on-merge setting.

Use Stop run in the run detail view or `t3-factory job-stop <jobId>` to request interruption. Factory resolves the current owning run from T3 and holds that T3 thread's queue while interrupting it, including remaining background work. If only PR watches remain, it ends those watches. A thread with no work is an accepted no-op. Success means the request was accepted; the scheduler keeps the job until a later T3 snapshot confirms its state. A rejection or lost response leaves ownership intact and reports an error. Inspect T3 before requesting Stop again after an uncertain outcome. Stop does not resume a queue, change a workspace, or grant merge authorization.

When a run's T3 thread was deleted, `t3-factory job-dismiss <jobId> [--reset-ticket]` clears the run. Factory first asks T3 for the thread and continues only when T3 answers `thread_not_found`. A readable thread, even an inactive one, is refused; use Stop or settle it in T3 instead. A network or authentication failure or an unexpected answer is refused without changes. On success the run is dismissed with a reason and time, releases its ticket claim, leaves active Runs and capacity, and the journal and status record it. Its workspace, branch and report are kept, and nothing new is started.

Without `--reset-ticket` the tracker is untouched. With it, Factory returns an in-progress ticket to the project's first ready status before dismissing, checking that status against the project's live columns, and reads the ticket back. An expired worker claim left by the deleted run is recovered and the ticket rescheduled to To do, which needs To do as the first ready status. A claim that has not expired may belong to a newer worker, so it is refused: retry after it expires, or dismiss without `--reset-ticket`. A ticket already in the ready status counts as done. Another status, or a claim older than the run, is refused. Any failure leaves the run and its claim in place for a retry. Repeating a finished dismissal succeeds without changes, and a retry after the ticket reset but the dismissal failed only dismisses.

The command runs in the scheduler when it is running. Otherwise the CLI claims the state directory and does the same work, so no restart or database edit is needed. If the scheduler took the request and stopped answering, the CLI reports the outcome as uncertain and does not repeat it; check `t3-factory status` first.

Stopping the service does not stop T3 work. Preserve the ledger, reports, tasks, and worktrees when investigating an uncertain run. T3 remains the place for notifications, human questions, and manual resumption.

## Review and merge

The configured `factorySkill` is the delivery workflow. For every ticket dispatch, Factory reads that file and includes its complete current text in the prompt, along with its source path for resolving references. Skill edits apply to the next dispatch without restarting Factory. A missing or empty skill blocks dispatch.

Factory authorizes merges when the supplied skill's current gates pass. The skill controls local review, Codex review, CI, regression proof, device validation, and holds. Factory adds no separate human merge-confirmation requirement. Existing threads retain the prompt they received until given updated instructions.

Automatic ticket runs replace the routine physical-phone checkpoint with agent-owned visual validation. The agent runs the changed build in the existing browser or simulator workflow, exercises the acceptance criteria, captures and inspects screenshots, and records and inspects video when static images cannot prove the interaction. Visual defects must be fixed and the evidence attached to the PR. Missing essential validation remains a concrete blocker; CI, review, regression proof, and holds still apply. Automatic runs do not request a user phone check. Manual runs keep the supplied skill's phone/device workflow, even when their model selection is `auto`.

When the supplied skill calls for Codex clean-review evidence, these helpers record the review baseline and check for a fresh reaction:

```sh
t3-factory approval-record OWNER/REPOSITORY PR_NUMBER /absolute/path/to/review-proof.json
t3-factory approval-check OWNER/REPOSITORY PR_NUMBER /absolute/path/to/review-proof.json
```

Only a fresh PR-body `+1` reaction from the verified Codex account, with an unchanged recorded head, satisfies the helper's clean-review evidence check. Old reactions, another actor, or a changed head do not. The skill also handles Codex reviews that contain findings and determines when a correction head needs another review.

The helper supplies review evidence, not the whole merge gate. Follow the supplied skill and use its expected-head guard when merging.

## macOS services and files

The default service label is `local.t3-factory`; `.web` identifies the web service and `.deploy` the optional release deployer. Substitute your `T3_FACTORY_SERVICE_LABEL` if overridden.

```sh
launchctl print "gui/$(id -u)/local.t3-factory"
launchctl bootout "gui/$(id -u)/local.t3-factory"
launchctl bootstrap "gui/$(id -u)" "$HOME/Library/LaunchAgents/local.t3-factory.plist"
```

The standard installer uses these paths:

| Path | Purpose |
| --- | --- |
| `~/.local/share/t3-factory/app` | Installed runtime and private `.env` copy |
| `~/.local/bin/t3-factory` | CLI launcher |
| `~/Library/LaunchAgents/<label>.plist` | User service definition |
| `~/Library/Logs/t3-factory*.log` | Scheduler, web and deployer logs |
| `~/.local/share/t3-factory/deploy` | Deployer checkout and last tried tag |
| `<stateDir>/state.sqlite` | Job ledger |
| `<stateDir>/reports` | Agent reports |

Re-run the relevant installer after source or environment changes. Existing configuration, credentials, and state are preserved. OIDC login sessions are stored privately under `stateDir` and survive web-service restarts. Caddy is operated separately; see [web access](web-access.md).

## Cleanup management

Open **Cleanup** to read Factory's persisted worktree catalog: every present worktree of a configured repository except its primary checkout, whether Factory, a T3 thread, or nothing at all created it. Page reads do not scan repositories, contact T3 or wait behind a deletion. Each row has one fixed height: the folder and branch, its project, one of four states, and a glyph whose tooltip gives the reason: **Unused** (delete rechecks it), **Blocked** (local changes or unmerged work; Delete anyway reviews it), **In use** (an open terminal, a running process or resumed work), or **Retrying** (automatic maintenance is mid-step). The segmented view narrows the list to one state; search and the Filter popover narrow by text, repository, owner and order. Free space is shown once per filesystem under the title. Size is unknown until a check reads the worktree.

**Delete N unused** rechecks every Unused candidate, including worktrees beyond the visible page and previous failures that no longer apply, and deletes those whose HEAD is merged into the configured remote release branch, by ancestry or by squash merge, with no tracked or untracked changes and no live owner, terminal or process. Idle T3 setup shells are closed first, like automatic maintenance does. Factory reports and tracker tickets are not required. Ignored files are deleted with the folder; tracked changes, untracked files, active work and unverified merge evidence preserve it. Press the select button in the title bar to pick rows; the selection bar then offers **Delete selected**; selected Blocked rows are reviewed and deleted anyway after one confirmation that says how many will lose work. Worktrees are deleted one at a time in list order, and each row shows Queued, Deleting… and then its result.

Each row expands to its path, branch, size, run/ticket/PR/thread links and last recorded result. **Check** starts a fresh bounded inspection inside the row; collapsing the row or cancelling stops it. **Delete anyway…** reviews a Blocked worktree and, when only content or merge holds remain, asks once what will be lost before deleting. Live safety checks are never overridden. Automatic cleanup timing and its last error stay collapsed below the list; a finished job whose worktree is already gone is finalized rather than retried.

Automatic maintenance also works through the catalog, so worktrees that no Factory run owns are reclaimed too. After the Factory jobs, each sweep checks catalog worktrees one at a time and deletes those that would pass **Delete N unused**: merged HEAD, no tracked or untracked changes, no live owner, terminal or process. Idle setup shells are closed first, and ignored caches go with the folder. Some worktrees are always skipped: primary checkouts, worktrees shared by several threads, and worktrees whose Factory job has not recorded its own cleanup. That last rule keeps Factory's completion checks and holds in force. A worktree is also skipped while a foreground cleanup command holds it, and while an earlier result is uncertain. It must also be idle for 24 hours: no thread activity, and no change to its top-level directory. The removal executor checks this again on its own fresh reading, before detaching and before deleting. Automatic maintenance never uses **Delete anyway…**. A refused candidate is checked again after about 15 minutes. Removals are recorded as cleanup actions by `automatic maintenance`, so a restart or cancellation never repeats a deletion. Repositories that are not configured are never touched.

Before a run starts, Factory reads the free space on the target repository's filesystem. If it is below `minFreeSpaceBytes`, the run is not started. The result is `disk-space-low`, with the path, available bytes and required bytes, and it points to Cleanup. If the space cannot be read, the run is not started either, and the result is `disk-space-check-failed`. Neither result takes a reservation or sends a launch. The check is only an admission threshold: a run can still fill the volume after it starts, and starting a run never deletes worktrees to make room.

Actions run independently of dispatch and reconciliation, ordered only against operations on the same job or worktree. The exclusive offline store claim still applies when no service is listening. Requests and outcomes persist across restarts and are visible in Cleanup and Activity. Cleanup operations do not appear in the Deck or other launch-request lists. An uncertain response holds automatic maintenance and further destructive requests for that path; it is never replayed. Inspect the directory, registration, bindings and recorded action to establish what actually happened. If verification shows a partial detach, a new review can proceed after a confirmed failure. Refreshing inspection can finalize an uncertain request only when fresh checks confirm both directory and registration absent and no remaining bindings. It records already-absent finalization with unknown removal attribution and no recovered-byte claim. Otherwise the hold remains for operator investigation.

The CLI accepts the same validated request on stdin through `t3-factory cleanup`. For example, the following only reads the inventory:

```sh
printf '%s\n' '{"type":"inventory","offset":0,"limit":50}' | t3-factory cleanup
```

Manual bulk deletion uses the shared inspection and removal executor, including final rechecks after idle bindings are detached. It reads the remote release tip without rewriting repository refs; stale local tracking refs cannot establish merge safety. Automatic maintenance and Retry now retain their Factory completion/report/tracker gates.

Factory refreshes the cleanup catalog in the background after job and removal changes, and on its normal reconciliation passes to discover external worktrees. Completed run state and verified removal outcomes appear from the ledger immediately, even before that sweep finishes. Refresh requests a background sweep and keeps the current list visible. The displayed discovery time stays unchanged until a successful scan; a failed refresh retains the last catalog and shows its error. Cached inventory is for browsing only: deletion always repeats the live safety checks.

## Backend concurrency and deployment checks

Manual starts have independent admission, cancellation and progress. Automatic work, provider checks, reconciliation, upstream discovery, session collection and cleanup no longer share a global worker. Only conflicting mutations on the same job or worktree are ordered. Automatic provider capacities and pause settings keep their existing meaning; increasing a capacity is not required to make manual requests independent.

Use the control-socket health response to inspect `operations`, per-operation stages/ages and event-loop delay. `work.active` remains available to older clients. Operation files and `manual-accepted` logs separate originating receipt, control receipt, scheduler acceptance and later phases. A provider failure with eligible tickets reports `no-ready-model`; inspect its safe cause instead of retrying an unchanged ticket. A pre-submission connection failure leaves no execution reservation. A possibly submitted launch retains its identity for reconciliation.

After a reviewed merge, back up the installed runtime and take a consistent SQLite backup, install the merged scheduler/web runtime using the setup guide, and verify installed file parity, service health, unchanged private settings, retained job/claim/history identities and concurrent non-launching checks. A dry-run response does not authorize a real launch. The source/history indexes and derived identity table are additive. Runtime rollback can retain the current ledger; restoring an older ledger over newly accepted requests would lose ownership evidence. Never replay uncertain requests as a deployment check.

A successful health response and named-ticket dry runs do not validate unnamed manual starts. Deployment verification must also exercise the user's actual model and overrides with no ticket key, repeat after ongoing thread activity, and verify read-only connection preflight. Dry runs stop before the final reservation/launch phase. When an already-authorized real start is available, observe its accepted thread and durable ownership rather than treating dry-run output as proof of a launch. Preserve the prior runtime until these checks pass. For rollback, unload both services and replace the runtime directory from the backup; merging dependency directories can retain incompatible files. Bootstrap the original loaded service labels and preserve current configuration and ledger.
